# 4. Identitäts- & Zugriffs-Ebene (Rechteverwaltung)

Konzept steht, Identitätsanbieter final bestätigt (M365/Entra-ID), Fallback-Mechanismus für externe Nutzer (OTP-Flow) fixiert. CORS-Policy folgt mit der Domain-/Frontend-Struktur.

*   **Identitätsanbieter:** Ein externer, OIDC-fähiger Identitätsanbieter übernimmt Login/Rollenzuweisung — kein eigenes Passwort-/Nutzerverwaltungssystem. Festgelegt: die bestehende M365/Entra-ID-Umgebung der Schule (Tenant-Zugriff für die App-Registrierung bestätigt), da die Nutzerkonten (Lehrer/Schüler) dort bereits existieren.
*   **Token-Validierung:** Signatur, Ablauf (`exp`/`nbf`) sowie Aussteller/Zielgruppe (`iss`/`aud`) müssen unabhängig vom konkreten Anbieter geprüft werden — sonst würde bei einer Multi-Tenant-fähigen Konfiguration ein Token aus *jedem* Tenant gültig durchgehen, nicht nur dem Schul-Tenant. Umsetzung: `PyJWT` mit `PyJWKClient` (JWKS-Fetch/Cache eingebaut) — aktiv gepflegt, von FastAPI selbst empfohlen; `python-jose` bewusst nicht verwendet (kaum noch gepflegt, offene Sicherheitswarnungen). Tokens sind signiert, nicht verschlüsselt — Claims sind für jeden mit dem Token lesbar, daher nicht als vertraulich behandeln (nicht mitloggen).
*   **Token-Lebensdauer:** Kurz- bis mittelfristig gültige Tokens ohne serverseitigen Widerruf (bei JWTs stateless) sind ein akzeptiertes Restrisiko statt einer eigenen Session-Blacklist — konkrete Lebensdauer folgt aus dem Anbieter-Standard.
*   **Autorisierung:** Rollen (z. B. Lehrer/Verwaltung/Admin) kommen aus dem Identitätsanbieter (Claim/Gruppe), die API entscheidet pro Endpoint — kein eigenes Rollensystem in der DB nötig. Schüler haben keinen eigenen Systemzugriff (`fachdomaenen.md` Abschnitt 5) und sind daher nie Träger einer Rolle. Die Rolle wirkt aber nur pro Endpoint, nicht pro Datensatz: die API braucht zusätzlich einen Ownership-Check in der Query (z. B. Erziehungsberechtigte sehen nur die Daten der eigenen zugeordneten Schüler), sonst IDOR-Risiko trotz korrekter Rolle.
*   **Zwei Zugriffswege, ein Endpunkt:** Mitarbeiter authentifizieren sich mit ihrem Tenant-Account im internen Frontend (Teams-App, `project-parts.md` Abschnitt 10) und rufen die Haupt-API direkt auf — das Frontend ist Public Client (Auth-Code + PKCE), die Entra-ID-Redirect-URI liegt deshalb dort und nicht bei der API, und das Backend validiert das mitgeschickte Token nur (oben). Für den Login hält es kein Client-Secret; das Secret der App-Registrierung dient allein dem App-only-Graph-Zugriff (`Mail.Send`, unten). Erziehungsberechtigte gehen dagegen über die Azure Function (`project-parts.md` Abschnitt 9), die ihre Anfragen kapselt und die API als einzige aufruft. Beide Wege treffen dieselbe API mit denselben Rollen- und Ownership-Prüfungen (`docs/adr/0001-fallback-through-main-api.md`).
*   **Bulk-Zugriff:** Der Ownership-Check schützt Einzeldatensätze, nicht eine Listen-/Export-Route (z. B. alle Adressen als CSV) — solche Endpunkte nur für interne Rollen mit ausdrücklicher Export-Berechtigung freigeben: Admin domänenübergreifend, Verwaltung für Stammdaten (`CONTEXT.md`; jede weitere Fachdomäne braucht eine eigene Berechtigung, keine automatische Ausweitung). **Nie über den OTP-Pfad** — ein Fallback-Token berechtigt ausschließlich zu Einzeldatensätzen der eigenen Familien, unabhängig davon, welche Rolle der Endpunkt sonst zulässt. Ein Export ist ein Lesezugriff, kein Datensatz-Update — erfasst wird er daher im Zentralen Logging (`idea/03-container-anwendung.md`), nicht im schreibbezogenen Audit-Trail.
*   **Fallback für externe Nutzer:** Erziehungsberechtigte ohne Zugang zum Identitätsanbieter der Schule bekommen Zugriff über einen OTP-Fluss statt eines Entra-ID-Logins — zwei getrennte Vertrauensgrenzen, analog zum Push-/Prune-Split (`idea/05-backup-recovery.md`). Ablauf: Nutzer gibt seine E-Mail-Adresse an, das Backend prüft, ob sie als `persons.email` **auf einer Person mit mindestens einer `family_guardians`-Zeile** hinterlegt ist (verhindert Angaben im Namen einer fremden Person oder Zugriff auf fremde Schülerdaten), verschickt bei Treffer einen Einmalcode an genau diese Adresse (Versand über Microsoft Graph API/Office365, kein zusätzlicher Dienstleister) und stellt nach korrekter Eingabe ein kurzlebiges, auf den Fallback-Pfad beschränktes Token aus. Zugriff läuft über die externe Azure Static Web App + Azure Function (oben), die mit diesem Token die Haupt-API aufruft. Löst das Risiko eines geteilten Dauer-Secrets von vornherein: der Code ist pro Login individuell, kein Per-Nutzer-Widerruf nötig. Voraussetzung im Datenmodell für den Ownership-Check ist die Familienzugehörigkeit (`family_guardians` → `families` → `children`, `domains/stammdaten.md`) — wer Mitglied einer Familie ist, sieht deren Kinder; bewusst keine eigene Erziehungsberechtigte↔Kind-Tabelle daneben. Steht bereits. Ist eine Person Mitglied mehrerer Familien (Patchwork), umfasst der Check die Kinder aller dieser Familien. Die Familienauswahl im Putzdienst (`domains/putzdienst.md`) ist Bedienführung für die Buchung, keine Sicherheitsgrenze — der Check darf sich nicht auf sie verlassen.
*   **Warum die Eintrittsbedingung die Familienzugehörigkeit mitprüft, nicht nur die Adresse:** Kinder bekommen eine `persons.email`, sobald die M365-Kontenverwaltung ihr Schulpostfach dorthin schreibt (`fachdomaenen.md` Abschnitt 6) — mittelfristig also für jeden Schüler. Ohne den Zusatz erfüllte jeder Schüler die Bedingung und bekäme einen gültigen Fallback-Token — für eine Gruppe, die `fachdomaenen.md` Abschnitt 5 ausdrücklich als „nur Datenobjekt, nie Akteur" definiert. Der Scope wäre zwar leer (der Ownership-Check läuft über `family_guardians`), aber die Trennung hinge dann daran, dass jeder künftige Endpunkt zusätzlich zur Token-Gültigkeit die Familienzugehörigkeit prüft — ein `EXISTS` mehr im OTP-Lookup ist der billigere Ort. Kein Schema-Eingriff: „wer darf einen Code anfordern" lässt sich nicht als Constraint ausdrücken. Aufstiegspfad, falls ein zweiter Aufrufer dazukommt: View `otp_eligible_persons` plus eigene DB-Rolle mit `SELECT` nur darauf, gleiches Muster wie bei den Art.-9-Spalten. Bewusst **nicht** hart constrainen lässt sich der verwandte Fall, dass eine Person zugleich `children`- und `guardians`-Zeile hat — ein ehemaliger Schüler, dessen Kind später hier ist, ist derselbe Mensch; die Eintrittsbedingung fängt ihn korrekt ab, ein CHECK wäre falsch.
*   **Nur natürliche Personen haben einen Zugangsweg:** Die OTP-Prüfung sieht ausschließlich `persons.email`, nie `organizations.email`. Erziehungsberechtigte können auch Organisationen sein (Jugendamt, Vereinsvormund, `domains/stammdaten.md`) — deren E-Mail ist ein rein ausgehender Kanal (die Schule schreibt die Behörde an), kein Identitätsanker: eine Behörden-Sammelmailbox belegt keine handelnde Person, und kein benannter Prozess verlangt, dass ein Sachbearbeiter selbst Schülerdaten abruft (`rules.md` Abschnitt 1). Folge ohne praktische Einschränkung: eine Familie, deren einzige Erziehungsberechtigte eine Organisation wäre, hätte keinen Elternzugang — dieser Fall kommt an der Schule nicht vor, Pflegeeltern werden immer als natürliche Person erfasst (`domains/stammdaten.md`).
*   **Mehrdeutige E-Mail-Prüfung:** `persons.email` ist bewusst **nicht** UNIQUE (`domains/stammdaten-schema.sql`, Begründung in `domains/stammdaten.md`, „Geteilte Mailbox") — ein Treffer kann mehrere Personen ergeben, weil sich real 1–2 Elternpaare je Klasse eine Mailbox teilen. Der Ownership-Check umfasst dann die Kinder der Familien **aller** Treffer; nach Code-Eingabe fragt die Oberfläche, als wer die Sitzung läuft. Diese Abfrage ist Bedienführung wie die Familienauswahl im Putzdienst, **keine Sicherheitsgrenze** — wer das Postfach hat, kann beide wählen, und mit UNIQUE wäre das nicht anders (dort landen bei erfundener Zweitadresse ebenfalls beide Codes in derselben Mailbox). E-Mail-Auth beweist nur Postfach-Zugriff, nie die Einzelperson dahinter; Prozesse mit echtem Einzelzustimmungsbedarf zwischen zwei Erziehungsberechtigten (z. B. Schulvertrag) lösen das deshalb nicht über die Login-Identität, sondern über eine eigene, explizite Zustimmungserfassung je Erziehungsberechtigtem samt Zustelladresse — vorgesehene Stelle: Anmeldeprozess-Fachdomäne, noch nicht gebaut.
*   **CORS:** Wird relevant, sobald Frontend(s) (Teams-Tab, externe Static-Web-Apps) und die API auf unterschiedlichen Origins liegen. Ob und welche CORS-Policy nötig ist, entscheidet sich mit der Domain-/App-Struktur (`pipeline/runbook.md`, DNS-Schritt).
