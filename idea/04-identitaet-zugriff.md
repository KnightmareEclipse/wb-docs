# 4. Identitäts- & Zugriffs-Ebene (Rechteverwaltung)

Konzept steht, Identitätsanbieter final bestätigt (M365/Entra-ID), Fallback-Mechanismus für externe Nutzer (OTP-Flow) fixiert. CORS-Policy folgt mit der Domain-/Frontend-Struktur.

*   **Identitätsanbieter:** Ein externer, OIDC-fähiger Identitätsanbieter übernimmt Login/Rollenzuweisung — kein eigenes Passwort-/Nutzerverwaltungssystem. Festgelegt: die bestehende M365/Entra-ID-Umgebung der Schule (Tenant-Zugriff für die App-Registrierung bestätigt), da die Nutzerkonten (Lehrer/Schüler) dort bereits existieren.
*   **Token-Validierung:** Signatur, Ablauf (`exp`/`nbf`) sowie Aussteller/Zielgruppe (`iss`/`aud`) müssen unabhängig vom konkreten Anbieter geprüft werden — sonst würde bei einer Multi-Tenant-fähigen Konfiguration ein Token aus *jedem* Tenant gültig durchgehen, nicht nur dem Schul-Tenant. Umsetzung: `PyJWT` mit `PyJWKClient` (JWKS-Fetch/Cache eingebaut) — aktiv gepflegt, von FastAPI selbst empfohlen; `python-jose` bewusst nicht verwendet (kaum noch gepflegt, offene Sicherheitswarnungen). Tokens sind signiert, nicht verschlüsselt — Claims sind für jeden mit dem Token lesbar, daher nicht als vertraulich behandeln (nicht mitloggen).
*   **Token-Lebensdauer:** Kurz- bis mittelfristig gültige Tokens ohne serverseitigen Widerruf (bei JWTs stateless) sind ein akzeptiertes Restrisiko statt einer eigenen Session-Blacklist — konkrete Lebensdauer folgt aus dem Anbieter-Standard.
*   **Autorisierung:** Rollen (z. B. Lehrer/Verwaltung/Admin) kommen aus dem Identitätsanbieter (Claim/Gruppe), die API entscheidet pro Endpoint — kein eigenes Rollensystem in der DB nötig. Schüler haben keinen eigenen Systemzugriff (`fachdomaenen.md` Abschnitt 5) und sind daher nie Träger einer Rolle. Die Rolle wirkt aber nur pro Endpoint, nicht pro Datensatz: die API braucht zusätzlich einen Ownership-Check in der Query (z. B. Erziehungsberechtigte sehen nur die Daten der eigenen zugeordneten Schüler), sonst IDOR-Risiko trotz korrekter Rolle.
*   **Bulk-Zugriff:** Der Ownership-Check schützt Einzeldatensätze, nicht eine Listen-/Export-Route (z. B. alle Adressen als CSV) — solche Endpunkte nur für die Admin-Rolle freigeben. Ein Export ist ein Lesezugriff, kein Datensatz-Update — erfasst wird er daher im Zentralen Logging (`idea/03-container-anwendung.md`), nicht im schreibbezogenen Audit-Trail.
*   **Fallback für externe Nutzer:** Erziehungsberechtigte ohne Zugang zum Identitätsanbieter der Schule bekommen Zugriff über einen OTP-Fluss statt eines Entra-ID-Logins — zwei getrennte Vertrauensgrenzen, analog zum Push-/Prune-Split (`idea/05-backup-recovery.md`). Ablauf: Nutzer gibt seine E-Mail-Adresse an, das Backend prüft, ob diese Adresse bei uns hinterlegt ist (verhindert Angaben im Namen einer fremden Person oder Zugriff auf fremde Schülerdaten), verschickt bei Treffer einen Einmalcode an genau diese Adresse (Versand über Microsoft Graph API/Office365, kein zusätzlicher Dienstleister) und stellt nach korrekter Eingabe ein kurzlebiges, auf den Fallback-Pfad beschränktes Token aus. Zugriff läuft über die externe Azure Static Web App + Azure Function (`project-parts.md` Abschnitt 9), die mit diesem Token dieselbe Haupt-API aufruft wie interne Nutzer — kein separater Zugriffsweg zur Datenbank (`docs/adr/0001-fallback-through-main-api.md`). Löst das Risiko eines geteilten Dauer-Secrets von vornherein: der Code ist pro Login individuell, kein Per-Nutzer-Widerruf nötig. Voraussetzung im Datenmodell: eine Zuordnung Erziehungsberechtigte↔Schüler, damit der Ownership-Check greift — Teil des Datenmodells der ersten Fachdomäne (Putzdienst, `fachdomaenen.md`).
*   **Mehrfachtreffer bei der E-Mail-Prüfung (geteilte Mailbox):** `persons.email` ist bewusst nicht eindeutig (`domains/stammdaten-schema.sql`) — zwei Erziehungsberechtigte können sich eine Mailbox teilen. Trifft die OTP-Prüfung mehrere Personen, ist das kein Fehlerfall: das Token bekommt Zugriff auf die Vereinigung der Familien aller Treffer (Haushalts-Session), ohne zwischen den Personen zu unterscheiden. Für `created_by`/`updated_by` wird deterministisch die zuerst angelegte der passenden `guardians`-Zeilen verwendet — kein neues Format nötig, die Ungenauigkeit ist akzeptiert (E-Mail-Auth beweist ohnehin nur Postfach-Zugriff, nie eine Einzelperson). Prozesse mit echtem Einzelzustimmungsbedarf zwischen zwei Erziehungsberechtigten (z. B. Schulvertrag) lösen das nicht über die Login-Identität, sondern über eine eigene, explizite Zustimmungserfassung je Erziehungsberechtigtem — vorgesehene Stelle: Anmeldeprozess-Fachdomäne, noch nicht gebaut.
*   **CORS:** Wird relevant, sobald Frontend(s) (Teams-Tab, externe Static-Web-Apps) und die API auf unterschiedlichen Origins liegen. Ob und welche CORS-Policy nötig ist, entscheidet sich mit der Domain-/App-Struktur (`pipeline/runbook.md`, DNS-Schritt).
