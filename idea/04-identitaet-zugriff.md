# 4. Identitäts- & Zugriffs-Ebene (Rechteverwaltung)

Konzept steht, Identitätsanbieter final bestätigt (M365/Entra-ID), OTP-Flow für externe Nutzer fixiert — verpflichtend für **jeden** externen Einstieg, auch den unbekannter Absender. CORS-Policy folgt mit der Domain-/Frontend-Struktur.

*   **Identitätsanbieter:** Ein externer, OIDC-fähiger Identitätsanbieter übernimmt Login/Rollenzuweisung — kein eigenes Passwort-/Nutzerverwaltungssystem. Festgelegt: die bestehende M365/Entra-ID-Umgebung der Schule (Tenant-Zugriff für die App-Registrierung bestätigt), da die Nutzerkonten (Lehrer/Schüler) dort bereits existieren.
*   **Token-Validierung:** Signatur, Ablauf (`exp`/`nbf`) sowie Aussteller/Zielgruppe (`iss`/`aud`) müssen unabhängig vom konkreten Anbieter geprüft werden — sonst würde bei einer Multi-Tenant-fähigen Konfiguration ein Token aus *jedem* Tenant gültig durchgehen, nicht nur dem Schul-Tenant. Umsetzung: `PyJWT` mit `PyJWKClient` (JWKS-Fetch/Cache eingebaut) — aktiv gepflegt, von FastAPI selbst empfohlen; `python-jose` bewusst nicht verwendet (kaum noch gepflegt, offene Sicherheitswarnungen). Tokens sind signiert, nicht verschlüsselt — Claims sind für jeden mit dem Token lesbar, daher nicht als vertraulich behandeln (nicht mitloggen).
*   **Token-Lebensdauer:** Kurz- bis mittelfristig gültige Tokens ohne serverseitigen Widerruf (bei JWTs stateless) sind ein akzeptiertes Restrisiko statt einer eigenen Session-Blacklist — konkrete Lebensdauer folgt aus dem Anbieter-Standard.
*   **Autorisierung:** Rollen (z. B. Lehrer/Verwaltung/Admin) kommen aus dem Identitätsanbieter (Claim/Gruppe), die API entscheidet pro Endpoint — kein eigenes Rollensystem in der DB nötig. Schüler haben keinen eigenen Systemzugriff (`fachdomaenen.md` Abschnitt 5) und sind daher nie Träger einer Rolle. Die Rolle wirkt aber nur pro Endpoint, nicht pro Datensatz: die API braucht zusätzlich einen Ownership-Check in der Query (z. B. Erziehungsberechtigte sehen nur die Daten der eigenen zugeordneten Schüler), sonst IDOR-Risiko trotz korrekter Rolle.
*   **Zwei Zugriffswege, ein Endpunkt:** Mitarbeiter authentifizieren sich mit ihrem Tenant-Account im internen Frontend (Teams-App, `project-parts.md` Abschnitt 10) und rufen die Haupt-API direkt auf — das Frontend ist Public Client (Auth-Code + PKCE), die Entra-ID-Redirect-URI liegt deshalb dort und nicht bei der API, und das Backend validiert das mitgeschickte Token nur (oben). Für den Login hält es kein Client-Secret; das Secret der App-Registrierung dient allein dem App-only-Graph-Zugriff (`Mail.Send`, unten). Erziehungsberechtigte gehen dagegen über die Azure Function (`project-parts.md` Abschnitt 9), die ihre Anfragen kapselt und die API als einzige aufruft. Beide Wege treffen dieselbe API mit denselben Rollen- und Ownership-Prüfungen. **Verworfen wurde dafür ein zweiter Backend-Vermittler mit eigenem Datenbankzugriff:** eine einzige exponierte Schnittstelle hält die Auth-/Ownership-Logik an einer Stelle (`rules.md` Abschnitt 3, „eine Konfigurationsquelle pro Sachverhalt") und öffnet keinen zweiten Netzwerkpfad in die Vertrauensgrenze hinein (`rules.md` Abschnitt 2, Zero-Trust). Die Datenbank bleibt deshalb für **jeden** Aufrufer ausschließlich über das interne Container-Netz erreichbar, unabhängig von der Zugriffsquelle (`idea/03-container-anwendung.md`).
*   **Bulk-Zugriff:** Der Ownership-Check schützt Einzeldatensätze, nicht eine Listen-/Export-Route (z. B. alle Adressen als CSV) — solche Endpunkte nur für interne Rollen mit ausdrücklicher Export-Berechtigung freigeben: Admin domänenübergreifend, Verwaltung für Stammdaten (`glossar.md`; jede weitere Fachdomäne braucht eine eigene Berechtigung, keine automatische Ausweitung). **Nie über den OTP-Pfad** — ein OTP-Token berechtigt ausschließlich zu Einzeldatensätzen der eigenen Familien, unabhängig davon, welche Rolle der Endpunkt sonst zulässt; das Anlege-Token unbekannter Absender liest überhaupt nichts (unten). Ein Export ist ein Lesezugriff, kein Datensatz-Update — erfasst wird er daher im Zentralen Logging (`idea/03-container-anwendung.md`), nicht im schreibbezogenen Audit-Trail.
*   **OTP-Pfad für externe Nutzer:** Wer keinen Zugang zum Identitätsanbieter der Schule hat, kommt über einen OTP-Fluss statt eines Entra-ID-Logins herein — zwei getrennte Vertrauensgrenzen, analog zum Push-/Prune-Split (`idea/05-backup-recovery.md`). Ablauf: Nutzer gibt seine E-Mail-Adresse an, das Backend verschickt einen Einmalcode an genau diese Adresse (Versand über Microsoft Graph API/Office365, kein zusätzlicher Dienstleister) und stellt nach korrekter Eingabe ein kurzlebiges, auf diesen Pfad beschränktes Token aus. Zugriff läuft über die externe Azure Static Web App + Azure Function (oben), die mit diesem Token die Haupt-API aufruft. Löst das Risiko eines geteilten Dauer-Secrets von vornherein: der Code ist pro Login individuell, kein Per-Nutzer-Widerruf nötig. **Der Fluss steht am Anfang jedes externen Vorgangs**, auch der öffentlichen Anmeldeformulare — es gibt keinen Weg an ihm vorbei und keine Wahl zwischen zwei Einstiegen. Die Code-Mail trägt den Code zum Abtippen **und** als Klick-Link, der die Sitzung direkt eröffnet: sie ist die Antwort auf eine soeben gestellte Anfrage, kurzlebig und einmal einlösbar, und niemand leitet sie weiter. Für Mails, die die Schule von sich aus verschickt, gilt das Gegenteil — dort darf ein Link nie selbst anmelden, weil Weiterleiten bei ihnen der Normalfall ist (`TODO-SESSIONS.md`, Voranmeldungs-Domäne).
*   **Zwei Scopes, ein Fluss:** Ob die Adresse als `persons.email` **auf einer Person mit mindestens einer `family_guardians`-Zeile** hinterlegt ist, entscheidet nicht über die Ausstellung des Codes, sondern über den Scope des Tokens danach. Treffer → Zugriff auf die Kinder der eigenen Familien; Voraussetzung im Datenmodell ist die Familienzugehörigkeit (`family_guardians` → `families` → `children`, `schema/stammdaten-schema.sql`) — wer Mitglied einer Familie ist, sieht deren Kinder; bewusst keine eigene Erziehungsberechtigte↔Kind-Tabelle daneben. Steht bereits. Ist eine Person Mitglied mehrerer Familien (Patchwork), umfasst der Check die Kinder aller dieser Familien. Kein Treffer → ein Token, das **ausschließlich anlegen darf und nichts liest**: es trägt die öffentlichen Anmeldeformulare (Voranmeldung, Ferienbuchung) und sonst nichts. Die Familienauswahl im Putzdienst (`schema/putzdienst-schema.sql`) ist Bedienführung für die Buchung, keine Sicherheitsgrenze — der Check darf sich nicht auf sie verlassen.
*   **Absenderpostfach und Scoping des Mailversands:** Jede vom System erzeugte Mail — der OTP-Code hier, dazu Bestätigungen, Erinnerungen und Rundmails der Fachdomänen (`schema/putzdienst-schema.sql`) — geht über `noreply@clemens.schule`. Das App-only-`Mail.Send` der App-Registrierung ist tenantweit, solange nichts es begrenzt: ohne **Application Access Policy** dürfte die Anwendung im Namen *jedes* Postfachs im Tenant senden, auch dem der Schulleitung. Die Policy wird deshalb auf eine mail-enabled Security Group mit genau diesem einen Postfach gesetzt (`TODO.md`) — dasselbe Muster wie `Sites.Selected` beim SharePoint-Zugriff (`project-parts.md` Abschnitt 10): enger Grant statt tenantweiter Berechtigung. **`Reply-To` zeigt dabei auf das Sekretariat**, nicht auf den Absender: das Postfach liest niemand, Eltern antworten aber auf Terminerinnerungen, und der Terminstausch läuft prozessseitig genau über diese Antwort (`schema/putzdienst-schema.sql`). Ohne Reply-To fiele sie ins Leere — und ein Prozess, der ins Leere läuft, wird an dieser Schule umgangen statt gemeldet (`fachdomaenen.md` Abschnitt 3).
*   **Warum jede Adresse einen Code bekommt, auch die unbekannte:** Drei Gründe, jeder für sich tragend. Der Dialog hört auf, ein **Orakel** über bekannte Adressen zu sein — die Antwort lautet für jede Eingabe „Code verschickt", und wer wissen will, ob eine Familie an der Schule ist, erfährt es hier nicht mehr. Der Absender hat **keine Wahl zwischen zwei Wegen**: ein bereits bekannter Elternteil landet nicht deshalb im leeren Formular, weil das der sichtbarere Knopf war, und legt dabei sein Kind ein zweites Mal an — der Scope entscheidet, nicht er (`TODO-SESSIONS.md`, Voranmeldungs-Domäne). Und jede Fremdanmeldung kommt mit **verifizierter Adresse** an, die für Buchungsbestätigung und Rückfragen ohnehin gebraucht wird; das ist zugleich die Begründung, die den Eltern gegenüber trägt.
*   **Was die Umstellung kostet und wo sie aufgefangen wird:** Der Mailversand geht jetzt auch an nie geprüfte Adressen — ohne **Rate-Begrenzung je Adresse und je Absender-IP** wird das Anforderungsformular ein Versandwerkzeug für Dritte. Die Begrenzung ist damit Teil des Flusses, nicht eine spätere Härtung. Der zweite Preis ist bezahlt, nicht offen: eine Kontaktperson, deren `persons.email` technisch befüllbar bleibt, obwohl `fachdomaenen.md` Abschnitt 5 sie als „nur Datenobjekt, nie Akteur" führt (`schema/stammdaten-schema.sql`), bekommt jetzt einen Anlege-Token statt gar keinen — der liest nichts und öffnet damit nichts. Die Trennung hängt am Scope statt an der Ausstellung, und dass sie dort trägt, muss jeder künftige Lese-Endpunkt voraussetzen. Für **Schüler** trägt zusätzlich das Schema: ihr Schulpostfach steht an `children.school_email` und nicht an `persons.email` (Begründung dort), kann die Scope-Bestimmung also gar nicht erst erreichen. Kein Schema-Eingriff: „welchen Scope bekommt diese Adresse" lässt sich nicht als Constraint ausdrücken. Aufstiegspfad, falls ein zweiter Aufrufer dazukommt: View `otp_eligible_persons` plus eigene DB-Rolle mit `SELECT` nur darauf, gleiches Muster wie bei den Art.-9-Spalten. Bewusst **nicht** hart constrainen lässt sich der verwandte Fall, dass eine Person zugleich `children`- und `guardians`-Zeile hat — ein ehemaliger Schüler, dessen Kind später hier ist, ist derselbe Mensch; die Scope-Bestimmung fängt ihn korrekt ab, ein CHECK wäre falsch.
*   **Jede Erziehungsberechtigte ist eine natürliche Person**, nie eine Institution (`schema/stammdaten-schema.sql`) — auch eine Amtsvormundin des Jugendamts ist eine `persons`-Zeile und bekommt deshalb einen OTP-Zugang wie jede andere. Das ist gewollt, kein übersehener Nebeneffekt: sie muss den Anmeldeprozess durchlaufen und den Schulvertrag zeichnen. Restrisiko, benannt: ihre Dienstadresse kann ein Funktionspostfach sein — dieselbe Klasse wie die geteilte Elternmailbox unten und mit derselben Begründung akzeptiert.
*   **Mehrdeutige E-Mail-Prüfung:** `persons.email` ist bewusst **nicht** UNIQUE (Begründung: `schema/stammdaten-schema.sql`) — ein Treffer kann deshalb mehrere Personen ergeben. Der Ownership-Check umfasst dann die Kinder der Familien **aller** Treffer; nach Code-Eingabe fragt die Oberfläche, als wer die Sitzung läuft. Diese Abfrage ist Bedienführung wie die Familienauswahl im Putzdienst, **keine Sicherheitsgrenze** — wer das Postfach hat, kann beide wählen. E-Mail-Auth beweist nur Postfach-Zugriff, nie die Einzelperson dahinter: Prozesse mit echtem Einzelzustimmungsbedarf lösen das deshalb nie über die Login-Identität, sondern über eine eigene Zustimmungserfassung je Erziehungsberechtigtem (`grenzkarte.md`, Q1).
*   **CORS:** Wird relevant, sobald Frontend(s) (Teams-Tab, externe Static-Web-Apps) und die API auf unterschiedlichen Origins liegen. Ob und welche CORS-Policy nötig ist, entscheidet sich mit der Domain-/App-Struktur (`pipeline/runbook.md`, DNS-Schritt).
