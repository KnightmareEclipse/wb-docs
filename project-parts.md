# Projekt-Teile (Umsetzungs-Workstreams)

Ableitung aus `idea/`, gruppiert nach konkreten Setup-Aufgaben statt nach Konzept-Kapiteln.

Abschnitt 1 (VPS/Host Setup) ist umgesetzt. Abschnitte 2–8 (App-Stack) sind in den Kernentscheidungen architektonisch fixiert und werden im App-Stack-Repo (`wb-backend`) umgesetzt — Compose-Stack, Backend-Grundgerüst, das vollständige Datenmodell als Modelle und Migrationen und die gemeinsame Schreibschicht stehen, einzelne Teilpunkte bleiben bewusst offen (siehe jeweiliger Abschnitt: Logging-Tool). Für die Abschnitte 9–10 (externe Frontends, Teams Apps) sind Hosting und Herkunftsschnitt entschieden (Abschnitt 9); die Werkzeugwahl **innerhalb** einer Oberfläche bleibt bewusst offen, bis das jeweilige Repo startet, damit ein Kurswechsel dort nicht die Doku umwirft.

1. **VPS / Host Setup** — Hetzners Standard-Debian-Cloud-Image (Debian 13), `cx33`/`fsn1`, Hetzner Cloud Firewall + UFW als zweite Ebene, verschlüsseltes Swap, unattended-upgrades mit festem Reboot-Fenster, Podman (rootful) als Basis für alles Weitere. Umgesetzt und im Detail begründet in `pipeline/vps-repo/01-provisioning.md` bis `03-podman-install.md`.
2. **Container Setup** — Netzwerk-Trennung extern/intern, Reverse-Proxy mit TLS-Terminierung (Caddy — automatisches HTTPS, kein Zugriff auf einen Runtime-Socket nötig), Container-Hardening, Secrets als gemountete Dateien statt Env-Vars. Images: PostgreSQL, Caddy, eigenes Backend-Image (Abschnitt 4). Details: `idea/03-container-anwendung.md`.
3. **Database Setup** — PostgreSQL 18, Least-Privilege-Rollen (Runtime/Migration/Backup, dazu enger geschnittene Rollen für Konfession, Bankverbindung, Gesundheitsmerkmale samt ihrer zweiten Stufe, Bewertung der Bewerbung, Küchenprofil und die Straf-Aussetzung des Putzdiensts — vollständige Liste in `TODO-SESSIONS.md`), Audit-Trail über DB-Trigger, erreichbar nur aus Backend + Backup. Details: `idea/03-container-anwendung.md`; Feldebene: `schema/stammdaten-schema.sql`, Rollen-Vokabular: `glossar.md`.
4. **API Development** — Backend-Service: Python, FastAPI + SQLAlchemy 2.0 (async) + Alembic-Migrationen, Dependency-Management über `pip` + `pip-tools` (Lockfile via `pip-compile`), Lint/Format über `ruff`, Typecheck über `mypy --strict`, OIDC-Token-Validierung über `PyJWT`, Constraint-Solver `ortools` für die Putzdienst-Restzuordnung, Zahlungsanbindung an Stripe für die drei Selbstservice-Anlässe (`grenzkarte.md`, Q3 — einziger Dienstleister mit Personendaten-Berührung, AVV in `idea/06-dsgvo-organisatorisch.md`), Tests über `pytest` vor jedem Deploy (lokal gegen den Compose-Stack, `rules.md` Abschnitt 9). Was die API dabei prüfen muss — Token-Validierung, Ownership-Check, Bulk-/Export-Regel — steht in `idea/04-identitaet-zugriff.md`.
5. **Identitätsanbieter-Setup** — App-/Rollen-Registrierung bei der bestehenden M365/Entra-ID-Umgebung der Schule (final bestätigt, Tenant-Zugriff vorhanden), Tenant-Restriktion. Fallback für Nutzer ohne Tenant-Zugang: OTP-Flow über dieselbe Haupt-API (`idea/04-identitaet-zugriff.md`). Die Redirect-URI zeigt auf `https://intern.clemens.schule` (Abschnitt 9), eine CORS-Policy entsteht nirgends.
6. **Logging & Monitoring** — healthchecks.io als Dead-Man's-Switch, bereits Teil des VPS-Setups (`pipeline/vps-repo/02-hardening.md`) und zugleich Alarmkanal für Backup- und GC-Fehlschläge. Zentrales Logging für Host + Container als **einzige offene Teilentscheidung** dieses Abschnitts: eine gemeinsame Senke statt eigenem Log-Stack, naheliegender Kandidat journald, endgültige Wahl folgt mit dem tatsächlichen Log-Volumen. Retention 30–90 Tage gilt unabhängig vom Tool (`idea/03-container-anwendung.md`).
7. **Backup & Recovery** — Pull statt Push: das NAS der Schule zieht den Dump per SSH, die VPS hält kein Offsite-Credential. Tools: `pg_dump`, `age`, DSM Task Scheduler. Ablauf, Alternativenprüfung und Restore-Test: `idea/05-backup-recovery.md`.
8. **GDPR / Organisatorisches** — AVV mit Hoster, Microsoft und healthchecks.io; die fixierte App-Stack-Architektur bringt keinen weiteren AVV-pflichtigen Dienstleister mit. Dazu Verarbeitungsverzeichnis, 72h-Meldeprozess, Löschfrist-Job. Details: `idea/06-dsgvo-organisatorisch.md`.
9. **Externe Frontends** — für **externe** Nutzer (z. B. Erziehungsberechtigte), für den Fallback-Zugriffsweg (Abschnitt 5): statische Oberfläche unter `portal.clemens.schule`, ausgeliefert vom Reverse-Proxy derselben VPS (Abschnitt 2). Ruft dieselbe `wb-backend`-Haupt-API wie interne Nutzer, mit einem eigenen, auf den Fallback-Pfad beschränkten Token, kein zweiter Zugriffsweg zur Datenbank (Begründung: `idea/04-identitaet-zugriff.md`, „Zwei Zugriffswege, ein Endpunkt"). Deploy über denselben Push wie der App-Stack (`pipeline/app-stack-repo/04-app-stack-deploy.md`), kein eigenes CI/CD.
    *   **Je Publikum eine eigene Herkunft, und zwar am Hostnamen.** Der Browser trennt an Schema+Host+Port, nicht am Pfad: Lägen Eltern- und Personaloberfläche auf demselben Host, könnte ein XSS in der öffentlich erreichbaren Elternoberfläche den Speicher der Personaloberfläche samt deren Entra-Token lesen — die schwächere Tür entscheidet dann über die stärkere. Daher `portal.clemens.schule` für Eltern und `intern.clemens.schule` fürs Personal (Abschnitt 10).
    *   **Jede Oberfläche ruft die API unter ihrer eigenen Herkunft:** der Reverse-Proxy hängt in jedem Host einen `/api/*`-Pfad auf denselben Backend-Container. Damit ist jede Anfrage gleichursprünglich — kein Preflight, keine Herkunfts-Allowlist, keine CORS-Policy, die jemand pflegt. `api.clemens.schule` bleibt als direkter Endpunkt für Health-Check, Monitoring und `curl` (`pipeline/runbook.md`); ein Browser ruft ihn nie.
    *   **Antwortköpfe setzt der Reverse-Proxy, je Host verschieden:** eine Content-Security-Policy, die nur eigene Skripte zulässt und weder fremde Quellen noch eine `base`-Umleitung kennt, dazu `X-Content-Type-Options: nosniff`. Damit läuft ein eingeschleustes Skript gar nicht erst — die erste Linie bleibt trotzdem, dass keine Oberfläche Text als HTML einsetzt. Der Preis, den man kennen muss: kein Inline-Skript und kein `onclick`-Attribut, der Build liefert Dateien aus. Die API selbst antwortet ausschließlich JSON und bekommt deshalb die schärfste Fassung; die Ausnahme für den Teams-Rahmen gilt allein `intern.` (Abschnitt 10).
    *   **Eine neue Subdomain entsteht nur mit einem neuen Publikum.** Voranmeldung, Ferienbuchung und Putzdienst teilen Publikum und Token — sie sind Seiten im Elternportal, keine eigenen Herkünfte.
    *   **Verworfen: Hosting über Azure Static Web Apps + Azure Functions.** Preis: Die API sähe nur noch Azure-Adressen — jede Begrenzung je Absender-IP wird damit wirkungslos, und der Zugriffslog trüge im Meldefall nach Art. 33 keine einzige echte Adresse (`idea/03-container-anwendung.md`). Dazu eine zweite Plattform mit eigenem CI/CD, eigenem Secret zwischen Function und API, eigenem Log und einem Verarbeiter mehr im Verzeichnis. Gekauft hätte sie den Frontend-Build außer Haus, Vorschau-Umgebungen je Pull Request und einen Rand, der einen Anwendungs-Flood abfängt, bevor er die VPS erreicht — Letzteres allerdings nur, wenn die API direkte Aufrufe ablehnt, wofür es stabile Ausgangs-IPs bräuchte, die der Consumption-Plan nicht hat. Gespart wird kein Geld: das freie Kontingent trägt dieses Volumen. Der Preis unserer Wahl ist, dass ein Anwendungs-Flood auf der VPS landet; abgefangen wird er dort, wo er wirkt — an der Rate-Begrenzung des OTP-Pfads (`idea/04-identitaet-zugriff.md`), nicht am Netzrand.
10. **Teams Apps** — für **Personal** (Staff), bilden größere, komplexere Prozesse ab (nicht nur einzelne Formulare) — daher voraussichtlich eine typisierte Sprache statt reinem JS (Kandidat: TypeScript, kompiliert als reine Dev-Dependency). Kein SPFx geplant — SPFx wäre nur nötig, wenn dieselbe UI zusätzlich als SharePoint-Web-Part laufen müsste, was hier nicht der Fall ist. Kein schweres UI-Framework standardmäßig; falls die Prozesskomplexität Struktur braucht, möglichst schlanke Wahl treffen, um die npm-Dependency-Kette (und damit den Patch-Aufwand) klein zu halten. Hosting wie die externen Frontends auf derselben VPS, unter `intern.clemens.schule` und mit demselben `/api/*`-Pfad (Abschnitt 9).
    *   **Drei Bedingungen, ohne die der Tab im Client leer bleibt** — keine davon ist ein Hosting-Detail, alle drei gelten für jede selbst ausgelieferte Teams-App: `Content-Security-Policy: frame-ancestors https://teams.microsoft.com https://*.cloud.microsoft` und **kein** `X-Frame-Options` (der Desktop-Client prüft strenger als der Browser); jede vom Tab berührte Domain samt Weiterleitungen in `validDomains` des Manifests, keine dynamischen Redirects daneben; HTTPS mit gültigem Zertifikat. Die getrennten Hosts aus Abschnitt 9 sind dafür Voraussetzung: Diese Ausnahme gilt nur `intern.`, während Elternportal und API `frame-ancestors 'none'` behalten — auf einem gemeinsamen Host wäre das Elternportal in Teams einbettbar.
    *   **Keine Cookie-Sitzung, nirgends.** Der Tab läuft als Drittkontext im iframe; Storage Partitioning (Chromium, Safari, Firefox) und blockierte Drittanbieter-Cookies brechen dort Cookie-Sitzungen ebenso wie iframe-basiertes Silent-SSO. Angemeldet wird über Teams-SSO (`getAuthToken` des Teams-SDK), weiter geht es mit dem Bearer-Token im Header — dieselbe Form, die das Backend ohnehin prüft (`idea/04-identitaet-zugriff.md`).
    *   **SharePoint-Dateispeicher:** unabhängig von der Tab-Technologie — Zugriff auf SharePoint-Dokumentbibliotheken erfolgt über Microsoft Graph API vom Backend aus, nicht über SPFx — als App-only-Berechtigung mit `Sites.Selected` (ein Admin grantet pro Bibliothek einzeln, kein tenantweiter Zugriff). Delegierter Zugriff wäre kein Sicherheitsgewinn: er bliebe ohnehin auf die vorhandenen SharePoint-Rechte des jeweiligen Nutzers begrenzt, die dieser über Teams/SharePoint auch direkt hat.
        *   **Zwei Bibliotheken, und die Bibliotheksgrenze ist die Zugriffsgrenze** (`grenzkarte.md`, Q2): in der einen legt die App die erzeugten Unterlagen ab und Menschen lesen nur, in der anderen arbeitet das Sekretariat wie bisher. Die App ist damit **nicht** der einzige Schreiber — das wäre auch keine Garantie, denn wer Zugriff auf eine Bibliothek hat, kann dort löschen; die Zusage „niemand ändert einen Vertrag still" trägt das Leserecht, nicht der Schreibweg. Direktzugriff bekommen ausschließlich Sekretariat und Geschäftsführung — sie sehen ohnehin alle Schüler und brauchen die Dateien im Alltag. Jede feinere Sicht (Zweig, Klasse, Kind) läuft über die API, die dieselbe Regel prüft wie für die Datenzeile — eine je Kind gepflegte SharePoint-Berechtigung wäre ein zweites Rechtesystem neben dem gebauten und liefe ihm hinterher.
        *   **Dokumenterzeugung:** Word-Vorlage mit Platzhaltern, gefüllt per `docxtpl` im Backend, PDF-Konvertierung über Graph (`content?format=pdf`, in der M365-Lizenz enthalten) — kein Konverter im Container, kein Premium-Konnektor, keine nutzungsabhängige Gebühr. Begründung und die verworfenen Alternativen in `schema/anmeldung-schema.sql`.

## Repo-Struktur

Aufteilung nach Lebenszyklus und Betriebsmodell statt einem einzigen Monorepo für alles — begründet durch die erwartete Anzahl an externen Frontends/Teams Apps, die sonst ein Repo unübersichtlich und für KI-Tools token-lastig machen würde, sowie durch den Unterschied manuell/selten (Host) vs. automatisiert/häufig (App-Deploys), damit App-Deploys keine dauerhaft lokal vorgehaltenen Secrets/Zugriffsrechte brauchen. Alle Repos liegen in einer gemeinsamen GitHub-Organisation (nicht GitLab — GitLab verlangt von jedem eingeladenen Mitglied bei der Anmeldung Kreditkartendaten), Namensschema `wb-<kurzname>` (Projektname „Weltenbaum").

*   **VPS-Repo** (`wb-vps`) — enthält `infra/` (hcloud-CLI-Skript für [Phase 1](pipeline/vps-repo/01-provisioning.md): Server + Firewall anlegen, Hetzners Standard-Debian-Image unverändert übernommen) und `ansible/` (laufende Host-Härtung ab [Phase 2](pipeline/vps-repo/02-hardening.md): Host-Key-Pflege, SSH-Härtung, Firewall, verschlüsseltes Swap, unattended-upgrades, Container-Runtime-Install; Ansible-Rollen statt selbst geschriebener Idempotenz, `rules.md` Abschnitt 1). Reine Host-Ebene: „VPS erstellen und verwalten", ändert sich selten und läuft weiter manuell/lokal (Root-SSH, pro Admin ein eigener Hetzner-API-Token statt eines geteilten). Legt außerdem einen eingeschränkten `deploy`-SSH-User an, über den das App-Stack-Repo andockt: Container startet unter rootful Podman Root, `deploy` darf per `sudo` genau eine systemd-Unit auslösen und sonst nichts ([Phase 3](pipeline/vps-repo/03-podman-install.md)). **Dieses Repo wird jetzt gebaut, bevor der App-Stack feststeht — ein nackter, sicherer, automatisiert aufgesetzter VPS ist unabhängig davon nutzbar.**
*   **App-Stack-Repo** (`wb-backend`) — enthält Compose-Setup (Abschnitt 2/3) und Backend-Code (Abschnitt 4). Ändert sich mit jedem App-/Container-Deploy; Build/Deploy laufen direkt auf der VPS über den `deploy`-User (kein externer CI-Runner, kein Hetzner-Token, kein Root-Zugriff nötig) — kein Drittanbieter hält einen Deploy-Key. Auslöser: Bare Git-Repo unter `deploy`, `post-receive`-Hook, Admin-Key per `git-shell`-Forced-Command beschränkt (`pipeline/app-stack-repo/04-app-stack-deploy.md`) — auf der VPS von [Phase 3](pipeline/vps-repo/03-podman-install.md) eingerichtet, ein Push deployt (`pipeline/runbook.md` Schritt 6).
*   **Teams-Apps-Repo** (geteilt, ein Ordner pro App) — Manifeste + Tab-Code sind voraussichtlich klein genug, dass ein gemeinsames Repo auch bei vielen Apps nicht unübersichtlich wird. Einzelne App wird erst ausgelagert, wenn sie eigenständig groß wird oder einen eigenen Release-Rhythmus braucht.
*   **Ein Repo pro externem Frontend** (Abschnitt 9) — jede hat vermutlich einen eigenen Build/Dependency-Baum. Ausgeliefert werden sie alle vom Reverse-Proxy der VPS, das Bau-Ergebnis kommt über denselben Push-Auslöser wie der App-Stack.

„yggdrasil" ist nur der lokale Arbeitsname dieses Verzeichnisses — keines der Repos trägt diesen Namen.
