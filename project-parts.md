# Projekt-Teile (Umsetzungs-Workstreams)

Ableitung aus `idea/`, gruppiert nach konkreten Setup-Aufgaben statt nach Konzept-Kapiteln.

Abschnitt 1 (VPS/Host Setup) ist umgesetzt. Abschnitte 2–8 (App-Stack) sind in den Kernentscheidungen architektonisch fixiert und werden im App-Stack-Repo (`wb-backend`) umgesetzt — Compose-Skeleton und Backend-Grundgerüst stehen, einzelne Teilpunkte bleiben bewusst offen (siehe jeweiliger Abschnitt: Logging-Tool, CORS). Abschnitte 9–10 (externe Frontends, Teams Apps) bleiben bewusst nur Toolkategorien — die Feinentscheidung folgt erst, wenn die jeweiligen Repos tatsächlich starten, damit ein Kurswechsel dort nicht die Doku umwirft.

1. **VPS / Host Setup** — Hetzners Standard-Debian-Cloud-Image, physische Sicherheit über Hetzners AVV (`pipeline/vps-repo/01-provisioning.md`), verschlüsseltes Swap mit zufälligem Boot-Schlüssel, SSH-Härtung (Host), Hetzner Cloud Firewall + UFW als zweite Ebene (inkl. `ufw limit` fürs SSH-Rate-Limiting), unattended-upgrades inkl. automatischem Reboot in festem Wartungsfenster, Rootless-Docker-Engine als Basis für alles Weitere.
2. **Docker / Container Setup** — Netzwerk-Trennung (extern/intern), Reverse-Proxy mit TLS-Terminierung (Caddy — automatisches HTTPS, kein Docker-Socket nötig), Container-Hardening (Non-Root, Read-Only-Rootfs, Resource-Limits), Secrets als Dateien statt Env-Vars. Images: PostgreSQL, Caddy, eigenes Backend-Image (Abschnitt 4).
3. **Database Setup** — PostgreSQL, Least-Privilege-Rollen (Runtime/Migration/Backup), Audit-Trail (`updated_by`/`updated_at` oder Trigger, Entscheidung folgt mit dem Schema-Design), Netzwerk-Isolation nur zu Backend + Backup.
4. **API Development** — Backend-Service: Python, FastAPI + SQLAlchemy 2.0 (async) + Alembic-Migrationen, Dependency-Management über `pip` + `pip-tools` (Lockfile via `pip-compile`), Lint/Format über `ruff`, Typecheck über `mypy --strict`. OIDC-Token-Validierung über `PyJWT` (Signatur, Aussteller/Zielgruppe, Ablauf), Ownership-Checks pro Endpoint (IDOR-Schutz), Bulk-/Export-Routen nur für Admin-Rolle, automatisierte Tests über `pytest` vor jedem Deploy (läuft lokal gegen Docker Compose, `rules.md` Abschnitt 9).
5. **Identitätsanbieter-Setup** — App-/Rollen-Registrierung bei der bestehenden M365/Entra-ID-Umgebung der Schule (final bestätigt, Tenant-Zugriff für die Registrierung vorhanden), da die Nutzerkonten dort bereits existieren, Tenant-Restriktion (kein Multi-Tenant-Fallstrick). Fallback-Zugriffsweg für Nutzer ohne Tenant-Zugang: OTP-Flow über dieselbe Haupt-API, kein separates Dauer-Secret (`idea/04-identitaet-zugriff.md`, `docs/adr/0001-fallback-through-main-api.md`). CORS-Policy folgt mit der Domain-/Frontend-Struktur (Abschnitt 9).
6. **Logging & Monitoring** — Host-Uptime-Monitoring als Dead-Man's-Switch über healthchecks.io (unabhängig von Docker/App-Stack, kostenloser Hobbyist-Plan, Hetzner Deutschland — eigener minimaler AVV, siehe `idea/06-dsgvo-organisatorisch.md`) für Reboot- + Disk-Space-Alerts — bereits Teil des VPS-Setups. Zentrales Logging für Host + Container (eine gemeinsame Senke statt eigenem Log-Stack, naheliegender Kandidat: das ohnehin vorhandene journald; endgültige Wahl folgt mit dem tatsächlichen Log-Volumen der App) — Retention 30–90 Tage bleibt als Vorgabe unabhängig vom Tool. Backup-Fehler-Alerting ist bereits entschieden: NAS-Cronjob meldet über healthchecks.io (`idea/05-backup-recovery.md`).
7. **Backup & Recovery** — Pull statt Push: das NAS der Schule (kein Cloud-CI-Runner) zieht den Dump per SSH von der VPS, die selbst kein Offsite-Credential hält und keinen Netzwerkpfad zum NAS. Dump über `pg_dump`, Verschlüsselung über `age` (skriptfähig ohne interaktiven Passphrase-Prompt), NAS-seitiger Auslöser über DSM Task Scheduler (nicht Active Backup for Business — das ist auf Datei-Sync ausgelegt, nicht auf On-Demand-Dump-Streaming). Gestaffelte Retention und Aufräumen laufen als NAS-eigene Administration, quartalsweiser Restore-Test auf der VPS.
8. **GDPR / Organisatorisches** — AVV mit Hoster, Microsoft und healthchecks.io; die fixierte App-Stack-Architektur bringt keinen weiteren AVV-pflichtigen Dienstleister mit (Details `idea/06-dsgvo-organisatorisch.md`), Verarbeitungsverzeichnis-Eintrag, 72h-Meldeprozess, Löschfrist-Job für Stammdaten.
9. **Externe Frontends** — für **externe** Nutzer (z. B. Erziehungsberechtigte), eigenes CI/CD pro App. Für den Fallback-Zugriffsweg (Abschnitt 5) festgelegt: Hosting über Azure Static Web Apps (kostenloses Kontingent), Backend über Azure Functions — ruft dieselbe `wb-backend`-Haupt-API auf wie interne Nutzer, mit einem eigenen, auf den Fallback-Pfad beschränkten Token, kein zweiter Zugriffsweg zur Datenbank (Begründung: `docs/adr/0001-fallback-through-main-api.md`). Konkreter CI/CD-Mechanismus folgt mit der App-Stack-Architektur.
10. **Teams Apps** — für **Personal** (Staff), bilden größere, komplexere Prozesse ab (nicht nur einzelne Formulare) — daher voraussichtlich eine typisierte Sprache statt reinem JS (Kandidat: TypeScript, kompiliert als reine Dev-Dependency). Kein SPFx geplant — SPFx wäre nur nötig, wenn dieselbe UI zusätzlich als SharePoint-Web-Part laufen müsste, was hier nicht der Fall ist. Kein schweres UI-Framework standardmäßig; falls die Prozesskomplexität Struktur braucht, möglichst schlanke Wahl treffen, um die npm-Dependency-Kette (und damit den Patch-Aufwand) klein zu halten. Hosting und Zugriff auf die Haupt-API (Entra-ID-Identität, interne Rollen) folgen mit der App-Stack-Architektur.
    *   **SharePoint-Dateispeicher:** unabhängig von der Tab-Technologie — Zugriff auf SharePoint-Dokumentbibliotheken erfolgt über Microsoft Graph API vom Backend aus, nicht über SPFx.

*Hinweis:* Umfang wächst noch — weitere Teile werden ergänzt, sobald sie konkret werden.

## Repo-Struktur

Aufteilung nach Lebenszyklus und Betriebsmodell statt einem einzigen Monorepo für alles — begründet durch die erwartete Anzahl an externen Frontends/Teams Apps, die sonst ein Repo unübersichtlich und für KI-Tools token-lastig machen würde, sowie durch den Unterschied manuell/selten (Host) vs. automatisiert/häufig (App-Deploys), damit Docker-Deploys keine dauerhaft lokal vorgehaltenen Secrets/Zugriffsrechte brauchen. Alle Repos liegen in einer gemeinsamen GitHub-Organisation (nicht GitLab — GitLab verlangt von jedem eingeladenen Mitglied bei der Anmeldung Kreditkartendaten), Namensschema `wb-<kurzname>` (Projektname „Weltenbaum").

*   **VPS-Repo** (`wb-vps`) — enthält `infra/` (hcloud-CLI-Skript für [Phase 1](pipeline/vps-repo/01-provisioning.md): Server + Firewall anlegen, Hetzners Standard-Debian-Image unverändert übernommen) und `setup/` (laufende Host-Härtung ab [Phase 2](pipeline/vps-repo/02-hardening.md): Host-Key-Pflege, SSH-Härtung, Firewall, verschlüsseltes Swap, unattended-upgrades, Docker-Engine-Install; ein idempotentes Shell-Skript statt Ansible, `rules.md` Abschnitt 1). Reine Host-Ebene: „VPS erstellen und verwalten", ändert sich selten und läuft weiter manuell/lokal (Root-SSH, pro Admin ein eigener Hetzner-API-Token statt eines geteilten). Legt außerdem einen eingeschränkten `deploy`-SSH-User an, über den das spätere App-Stack-Repo andockt. Dieser `deploy`-User betreibt einen Rootless-Docker-Daemon statt Zugriff auf einen root-eigenen Docker-Socket zu bekommen — macht den Root-Ausschluss technisch verbindlich, Begründung in [Phase 3](pipeline/vps-repo/03-docker-install.md). **Dieses Repo wird jetzt gebaut, bevor der App-Stack feststeht — ein nackter, sicherer, automatisiert aufgesetzter VPS ist unabhängig davon nutzbar.**
*   **App-Stack-Repo** (`wb-backend`) — enthält Compose-Setup (Abschnitt 2/3) und Backend-Code (Abschnitt 4). Ändert sich mit jedem App-/Container-Deploy; Build/Deploy laufen direkt auf der VPS über den `deploy`-User (kein externer CI-Runner, kein Hetzner-Token, kein Root-Zugriff nötig) — kein Drittanbieter hält einen Deploy-Key. Auslöser: Bare Git-Repo unter `deploy`, `post-receive`-Hook, Admin-Key per `git-shell`-Forced-Command beschränkt (`pipeline/app-stack-repo/04-app-stack-deploy.md`) — auf der VPS noch nicht bootstrappt (`pipeline/runbook.md` Schritt 5).
*   **Teams-Apps-Repo** (geteilt, ein Ordner pro App) — Manifeste + Tab-Code sind voraussichtlich klein genug, dass ein gemeinsames Repo auch bei vielen Apps nicht unübersichtlich wird. Einzelne App wird erst ausgelagert, wenn sie eigenständig groß wird oder einen eigenen Release-Rhythmus braucht.
*   **Ein Repo pro externem Frontend** (Abschnitt 9) — jede hat vermutlich einen eigenen Build/Dependency-Baum; falls Azure Static Web Apps die gewählte Plattform wird, folgt daraus deren Eins-Repo-pro-App-CI/CD-Konvention.

„yggdrasil" ist nur der lokale Arbeitsname dieses Verzeichnisses — keines der Repos trägt diesen Namen.
