# Projekt-Teile (Umsetzungs-Workstreams)

Ableitung aus `idea/`, gruppiert nach konkreten Setup-Aufgaben statt nach Konzept-Kapiteln.

1. **VPS / Host Setup** — LUKS Full-Disk-Encryption, Dropbear-im-Initramfs Remote-Unlock (statische IP), SSH-Härtung (Host + Dropbear), Hetzner Cloud Firewall + UFW als zweite Ebene, fail2ban, unattended-upgrades (ohne Auto-Reboot) inkl. Kernel-Update-Hook (`update-initramfs`/`update-grub`).
2. **Docker / Container Setup** — Netzwerk-Trennung (extern/intern), Caddy Reverse-Proxy + TLS, Container-Hardening (Non-Root, Read-Only-Rootfs, Resource-Limits), Secrets-als-Dateien (`/run/secrets`).
3. **Database Setup (PostgreSQL)** — Least-Privilege-Rollen (Runtime/Migration/Backup), Audit-Trail (`updated_by`/`updated_at` oder Trigger), Netzwerk-Isolation nur zu API+Backup.
4. **API Development** — Python-Service, OIDC-Token-Validierung (JWKS, `iss`/`aud`/`exp`/`nbf`), Ownership-Checks pro Endpoint (IDOR-Schutz), Bulk-/Export-Routen nur für Admin-Rolle.
5. **Azure / Entra ID Setup** — App-Registrierung, App Roles/Gruppen → `roles`-Claim, Tenant-Restriktion (kein `/common/`-Multi-Tenant-Fallstrick), Azure Functions Fallback mit Function-Key + separatem Secret zur API.
6. **Logging & Monitoring** — journald als einzige Log-Senke für Host + Container (Docker-Log-Treiber `journald`), Retention-Policy (30–90 Tage), Host-Uptime-Monitoring als Dead-Man's-Switch über healthchecks.io (unabhängig von Docker, kostenloser Hobbyist-Plan, Hetzner Deutschland — eigener minimaler AVV, siehe `idea/06-dsgvo-organisatorisch.md`) für Reboot- + Disk-Space-Alerts, Backup-Fehler-Alerting.
7. **Backup & Recovery** — Restic-Cronjob (Push-Only-Credential), Offsite-Transfer mit getrennten Push-/Prune-Credentials, Retention-Policy (`forget`/`prune`, manuell), quartalsweiser Restore-Test.
8. **GDPR / Organisatorisches** — AVV mit Hoster, Microsoft und healthchecks.io, Verarbeitungsverzeichnis-Eintrag, 72h-Meldeprozess, Löschfrist-Job für Stammdaten.
9. **Azure Static Web Apps** — Frontend(s) für **externe** Nutzer, eigene CI/CD (GitLab CI mit der SWA-CLI + Deployment-Token, da Azure Static Web Apps im Portal-Wizard nativ nur GitHub/Azure DevOps anbietet), Zugriff auf die DB nur indirekt über die Azure Functions (Abschnitt 4 Fallback-Pfad), nicht direkt über die Haupt-API.
10. **Teams Apps** — für **Personal** (Staff), bilden größere, komplexere Prozesse ab (nicht nur einzelne Formulare) — daher **TypeScript** statt reinem JS, kompiliert via `tsc` (reine Dev-Dependency, keine Laufzeit-Abhängigkeit). Kein SPFx — SPFx wäre nur nötig, wenn dieselbe UI zusätzlich als SharePoint-Web-Part laufen müsste, was hier nicht der Fall ist. Kein schweres UI-Framework standardmäßig; falls die Prozesskomplexität Struktur braucht, möglichst schlanke Wahl treffen, um die npm-Dependency-Kette (und damit den Patch-Aufwand) klein zu halten. Gehostet über den eigenen Caddy/VPS statt Azure, greift direkt über die Haupt-API zu (Entra-ID-Identität, interne Rollen).
    *   **SharePoint-Dateispeicher:** unabhängig von der Tab-Technologie — Zugriff auf SharePoint-Dokumentbibliotheken erfolgt über Microsoft Graph API vom API-Backend aus, nicht über SPFx.

*Hinweis:* Umfang wächst noch — weitere Teile werden ergänzt, sobald sie konkret werden.

## Repo-Struktur

Aufteilung nach Lebenszyklus und Betriebsmodell statt einem einzigen Monorepo für alles — begründet durch die erwartete Anzahl an Static Web Apps/Teams Apps, die sonst ein Repo unübersichtlich und für KI-Tools token-lastig machen würde, sowie durch den Unterschied manuell/selten (Host) vs. automatisiert/häufig (App-Deploys), damit Docker-Deploys keine dauerhaft lokal vorgehaltenen Secrets/Zugriffsrechte brauchen:

*   **VPS-Repo** (lokal `vps/`, eigener Name folgt später) — enthält `infra/` (hcloud-CLI-Skript für [Phase 1](pipeline/vps-repo/01-provisioning.md) sowie das Rescue-Skript für die einmalige LUKS/Dropbear-Ersteinrichtung in [Phase 2](pipeline/vps-repo/02-rescue-install.md), `idea/01-boot-verschluesselung.md`/`idea/02-netzwerk-firewall.md`) und `setup/` (laufende Host-Härtung ab [Phase 4](pipeline/vps-repo/04-hardening.md): Dropbear-/Host-Key-Pflege, SSH-Härtung, Firewall, unattended-upgrades, Docker-Engine-Install — `idea/01-boot-verschluesselung.md`; ein idempotentes Shell-Skript statt Ansible — bei genau einer VPS mit statischer IP derselbe „Overkill"-Grund wie der Terraform-Verzicht in [Phase 1](pipeline/vps-repo/01-provisioning.md)). Reine Host-Ebene: „VPS erstellen und verwalten", ändert sich selten und läuft weiter manuell/lokal (Root-SSH, pro Admin ein eigener Hetzner-API-Token statt eines geteilten) — passt zum ohnehin manuellen LUKS-Unlock (`idea/01-boot-verschluesselung.md`). Legt außerdem einen eingeschränkten `deploy`-SSH-User an, über den das App-Stack-Repo andockt. Dieser `deploy`-User betreibt einen Rootless-Docker-Daemon ([Phase 5a](pipeline/vps-repo/05a-docker-install.md)) statt Zugriff auf einen root-eigenen Docker-Socket zu bekommen — macht den Root-Ausschluss technisch verbindlich.
*   **App-Stack-Repo** (lokal `app-stack/`, eigener Name folgt später) — enthält `compose/` (Abschnitt 3) und `api/` (Abschnitt 4). Ändert sich mit jedem App-/Container-Deploy, läuft deshalb über eigene CI/CD (GitLab CI, gitlab.com) gegen den `deploy`-User statt über die lokale Admin-Maschine — kein Hetzner-Token und kein Root-Zugriff nötig, nur ein eingeschränkter, in der CI rotierbarer Deploy-Key statt dauerhaft lokal vorgehaltener DB-/OIDC-/Restic-Secrets. Images werden in der projekteigenen GitLab Container Registry gebaut/versioniert, nicht auf der VPS selbst.
*   **Teams-Apps-Repo** (geteilt, ein Ordner pro App) — Manifeste + TypeScript-Tab-Code sind klein genug, dass ein gemeinsames Repo auch bei vielen Apps nicht unübersichtlich wird. Einzelne App wird erst ausgelagert, wenn sie eigenständig groß wird oder einen eigenen Release-Rhythmus braucht.
*   **Ein Repo pro Static Web App** (Abschnitt 9) — jede hat eigenen Build/Dependency-Baum und folgt Azure Static Web Apps' Eins-Repo-pro-App-CI/CD-Konvention (inkl. gepaarter „managed" Azure Function im selben Repo).

„cyborg" ist nur der lokale Arbeitsname dieses Verzeichnisses — keines der Repos trägt diesen Namen.
