# Projekt-Teile (Umsetzungs-Workstreams)

Ableitung aus `idea/`, gruppiert nach konkreten Setup-Aufgaben statt nach Konzept-Kapiteln.

Abschnitt 1 (VPS/Host Setup) wird jetzt konkret umgesetzt. Alle anderen Abschnitte beschreiben bewusst nur Toolkategorien und grobe Architektur, keine konkreten Frameworks/Produkte — die Feinentscheidung fällt erst, wenn die App-Stack-Entwicklung tatsächlich beginnt, damit ein Kurswechsel während der Entwicklung nicht die Doku umwerfen muss.

1. **VPS / Host Setup** — Hetzners Standard-Debian-Cloud-Image, physische Sicherheit über Hetzners AVV (`idea/01-boot-verschluesselung.md`), verschlüsseltes Swap mit zufälligem Boot-Schlüssel, SSH-Härtung (Host), Hetzner Cloud Firewall + UFW als zweite Ebene (inkl. `ufw limit` fürs SSH-Rate-Limiting), unattended-upgrades inkl. automatischem Reboot in festem Wartungsfenster, Rootless-Docker-Engine als Basis für alles Weitere.
2. **Docker / Container Setup** — Netzwerk-Trennung (extern/intern), Reverse-Proxy mit TLS-Terminierung (Tool offen), Container-Hardening (Non-Root, Read-Only-Rootfs, Resource-Limits), Secrets als Dateien statt Env-Vars. Konkrete Images/Tools folgen mit der App-Stack-Architektur.
3. **Database Setup** — relationale Datenbank (konkretes System offen), Least-Privilege-Rollen (Runtime/Migration/Backup), Audit-Trail (`updated_by`/`updated_at` oder Trigger), Netzwerk-Isolation nur zu Backend + Backup.
4. **API Development** — Backend-Service (Sprache/Framework offen), OIDC-Token-Validierung (Signatur, Aussteller/Zielgruppe, Ablauf), Ownership-Checks pro Endpoint (IDOR-Schutz), Bulk-/Export-Routen nur für Admin-Rolle, automatisierte Tests vor jedem Deploy (Test-Framework offen, läuft lokal gegen Docker Compose, `rules.md` Abschnitt 9).
5. **Identitätsanbieter-Setup** — App-/Rollen-Registrierung beim gewählten Identitätsanbieter (naheliegender Kandidat: die bestehende M365/Entra-ID-Umgebung der Schule, da die Nutzerkonten dort bereits existieren), Tenant-Restriktion (kein Multi-Tenant-Fallstrick), ein Fallback-Zugriffsweg mit separatem Secret für Nutzer ohne Zugang zu diesem Tenant. Konkreter Mechanismus folgt mit der App-Stack-Architektur.
6. **Logging & Monitoring** — Host-Uptime-Monitoring als Dead-Man's-Switch über healthchecks.io (unabhängig von Docker/App-Stack, kostenloser Hobbyist-Plan, Hetzner Deutschland — eigener minimaler AVV, siehe `idea/06-dsgvo-organisatorisch.md`) für Reboot- + Disk-Space-Alerts — bereits Teil des VPS-Setups. Zentrales Logging für Host + Container (eine gemeinsame Senke statt eigenem Log-Stack, naheliegender Kandidat: das ohnehin vorhandene journald) sowie Backup-Fehler-Alerting folgen mit der App-Stack-Architektur; Retention 30–90 Tage bleibt als Vorgabe unabhängig vom Tool.
7. **Backup & Recovery** — Cronjob mit Push-Only-Credential, Offsite-Transfer mit getrennten Push-/Prune-Credentials, gestaffelte Retention (manuelles Aufräumen), quartalsweiser Restore-Test. Konkretes Tool und Offsite-Ziel folgen mit der App-Stack-Architektur (naheliegender Kandidat für das Ziel: der bestehende M365-Tenant der Schule).
8. **GDPR / Organisatorisches** — AVV mit Hoster, Microsoft und healthchecks.io (weitere Dienstleister-AVVs folgen mit der App-Stack-Architektur), Verarbeitungsverzeichnis-Eintrag, 72h-Meldeprozess, Löschfrist-Job für Stammdaten.
9. **Externe Frontends** — für **externe** Nutzer (z. B. Erziehungsberechtigte), eigenes CI/CD pro App, Zugriff auf die DB nur indirekt über einen Backend-Vermittler (Abschnitt 5 Fallback-Pfad), nicht direkt über die Haupt-API. Konkrete Hosting-Plattform (Kandidat: Azure Static Web Apps wegen kostenlosem Kontingent) und CI/CD-Mechanismus folgen mit der App-Stack-Architektur.
10. **Teams Apps** — für **Personal** (Staff), bilden größere, komplexere Prozesse ab (nicht nur einzelne Formulare) — daher voraussichtlich eine typisierte Sprache statt reinem JS (Kandidat: TypeScript, kompiliert als reine Dev-Dependency). Kein SPFx geplant — SPFx wäre nur nötig, wenn dieselbe UI zusätzlich als SharePoint-Web-Part laufen müsste, was hier nicht der Fall ist. Kein schweres UI-Framework standardmäßig; falls die Prozesskomplexität Struktur braucht, möglichst schlanke Wahl treffen, um die npm-Dependency-Kette (und damit den Patch-Aufwand) klein zu halten. Hosting und Zugriff auf die Haupt-API (Entra-ID-Identität, interne Rollen) folgen mit der App-Stack-Architektur.
    *   **SharePoint-Dateispeicher:** unabhängig von der Tab-Technologie — Zugriff auf SharePoint-Dokumentbibliotheken erfolgt über Microsoft Graph API vom Backend aus, nicht über SPFx.

## Repo-Struktur

Aufteilung nach Lebenszyklus und Betriebsmodell statt einem einzigen Monorepo für alles — begründet durch die erwartete Anzahl an externen Frontends/Teams Apps, die sonst ein Repo unübersichtlich und für KI-Tools token-lastig machen würde, sowie durch den Unterschied manuell/selten (Host) vs. automatisiert/häufig (App-Deploys), damit Docker-Deploys keine dauerhaft lokal vorgehaltenen Secrets/Zugriffsrechte brauchen. Alle Repos liegen in einer gemeinsamen GitHub-Organisation (nicht GitLab — GitLab verlangt von jedem eingeladenen Mitglied bei der Anmeldung Kreditkartendaten), Namensschema `wb-<kurzname>` (Projektname „Weltenbaum").

*   **VPS-Repo** (`wb-vps`) — enthält `infra/` (hcloud-CLI-Skript für [Phase 1](pipeline/vps-repo/01-provisioning.md): Server + Firewall anlegen, Hetzners Standard-Debian-Image unverändert übernommen, `idea/01-boot-verschluesselung.md`/`idea/02-netzwerk-firewall.md`) und `setup/` (laufende Host-Härtung ab [Phase 2](pipeline/vps-repo/02-hardening.md): Host-Key-Pflege, SSH-Härtung, Firewall, verschlüsseltes Swap, unattended-upgrades, Docker-Engine-Install — `idea/01-boot-verschluesselung.md`; ein idempotentes Shell-Skript statt Ansible, `rules.md` Abschnitt 1). Reine Host-Ebene: „VPS erstellen und verwalten", ändert sich selten und läuft weiter manuell/lokal (Root-SSH, pro Admin ein eigener Hetzner-API-Token statt eines geteilten). Legt außerdem einen eingeschränkten `deploy`-SSH-User an, über den das spätere App-Stack-Repo andockt. Dieser `deploy`-User betreibt einen Rootless-Docker-Daemon ([Phase 3](pipeline/vps-repo/03-docker-install.md)) statt Zugriff auf einen root-eigenen Docker-Socket zu bekommen — macht den Root-Ausschluss technisch verbindlich (schützt einen kompromittierten CI-Deploy-Key, nicht die eigenen Admins, `rules.md` Abschnitt 2). **Dieses Repo wird jetzt gebaut, bevor der App-Stack feststeht — ein nackter, sicherer, automatisiert aufgesetzter VPS ist unabhängig davon nutzbar.**
*   **App-Stack-Repo** (lokal `app-stack/`, eigener Name folgt später) — enthält perspektivisch Compose-Setup (Abschnitt 2/3) und Backend-Code (Abschnitt 4). Ändert sich mit jedem App-/Container-Deploy, läuft deshalb über eine eigene CI/CD gegen den `deploy`-User statt über die lokale Admin-Maschine — kein Hetzner-Token und kein Root-Zugriff nötig, nur ein eingeschränkter, in der CI rotierbarer Deploy-Key statt dauerhaft lokal vorgehaltener Secrets. Konkrete CI/CD-Plattform, Registry und Tool-Wahl folgen, sobald die App-Stack-Architektur ansteht.
*   **Teams-Apps-Repo** (geteilt, ein Ordner pro App) — Manifeste + Tab-Code sind voraussichtlich klein genug, dass ein gemeinsames Repo auch bei vielen Apps nicht unübersichtlich wird. Einzelne App wird erst ausgelagert, wenn sie eigenständig groß wird oder einen eigenen Release-Rhythmus braucht.
*   **Ein Repo pro externem Frontend** (Abschnitt 9) — jede hat vermutlich einen eigenen Build/Dependency-Baum; falls Azure Static Web Apps die gewählte Plattform wird, folgt daraus deren Eins-Repo-pro-App-CI/CD-Konvention.

„yggdrasil" ist nur der lokale Arbeitsname dieses Verzeichnisses — keines der Repos trägt diesen Namen.
