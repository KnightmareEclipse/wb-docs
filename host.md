# Host — Server, Firewall, Härtung

Hetzners Standard-Debian-Cloud-Image (Debian 13), `cx33`/`fsn1`, Hetzner Cloud Firewall und UFW als
zweite Ebene, verschlüsseltes Swap, unattended-upgrades mit festem Reboot-Fenster. Umgesetzt in
`wb-vps/infra/` (Server und Cloud Firewall) und `wb-vps/ansible/roles/hardening/` (alles auf dem
Host); die Container-Runtime darüber steht in `container.md`, der Ablauf für einen Neuaufbau in
`runbook.md`.

## Server und Cloud Firewall

Idempotentes Skript gegen das offizielle `hcloud`-CLI:

*   Prüft per `hcloud server describe` anhand des festen Servernamens `db-prod-fsn-01` + Hetzner-Label `weltenbaum` (beide als Konstante in `wb-vps/infra/`), ob der Server schon existiert, legt ihn sonst neu an.
*   Die Firewall wird davon unabhängig bei jedem Skriptlauf idempotent auf den Soll-Zustand aus `ports.yml` gebracht (`hcloud firewall`-Regeln per festem Namen anlegen falls fehlend, sonst per `set-rules` synchronisieren) — nicht nur bei Server-Neuanlage, damit spätere `ports.yml`-Änderungen auch gegen einen bereits bestehenden Server automatisiert nachgezogen werden. Jede Freigabe-Regel wird für beide Quell-Familien gesetzt (`0.0.0.0/0` **und** `::/0`) — Hetzner wendet eine Regel nicht automatisch auf beide an, sonst bliebe der IPv6-Pfad (Hetzners natives Dual-Stack-Networking auf dem Standard-Image) ungefiltert.
*   Zero-Trust nach außen: eingehend per Default nur Port 22 (SSH) sowie 80/443 (späterer öffentlicher App-Stack-Dienst) offen, alles andere zu. Datenbank-/Backend-Ports bleiben nach außen komplett geschlossen — welche das konkret sind, entscheidet sich mit der App-Stack-Architektur. **Akzeptiertes Risiko:** kein Egress-Filtering — Schutzziel ist der eingehende Zugriff, nicht Exfiltration nach einem Einbruch.
*   **Kein eigenes DDoS-Mitigation-Tool (bewusst):** andere Bedrohung als der Bruteforce-Schutz aus der Härtung unten — DDoS ist Ressourcenerschöpfung durch Volumen (SYN-/Bandbreiten-Flood), kein Credential-Raten, `ufw limit` (SSH-Rate-Limiting) wirkt hier nicht. Hetzner filtert volumetrische Angriffe bereits am Netzwerk-Perimeter, bevor Traffic die VPS erreicht — Hoster-native Lösung statt Eigenbau (`rules.md` Abschnitt 1 Punkt 2, Abschnitt 2 Vertrauensgrenze: Hetzner gilt als vertrauenswürdig).
*   Servertyp `cx33` (4 vCPU shared, 8GB RAM, 80GB NVMe SSD — für den späteren App-Stack einer kleinen Schule ausreichend dimensioniert), Region `fsn1` (Falkenstein, Deutschland — einfachste DSGVO-Begründung ohne Drittland-Transfer), beide als Konstante in `wb-vps/infra/`.
*   `--image debian-13` ist das tatsächlich laufende Image — Hetzners Standard-Cloud-Image, unverändert übernommen, kein eigener Wipe-/Rescue-/Installationsschritt, kein individuelles Partitionslayout. Die Version ist nicht beliebig: Debian 13 (trixie) liefert Podman 5.4, Debian 12 nur 4.3 — die Eigenschaften, auf denen die Container-Runtime beruht (`container.md`), hängen daran. Die Admin-Public-Keys aus `wb-vps/setup/admins.yml` (bewusst dieselbe einzige Key-Quelle wie in Phase 2, `rules.md` Abschnitt 3 — liegt in `setup/`, wird aber auch hier vom `infra/`-Skript gelesen) werden vom Skript zuvor idempotent als Hetzner-SSH-Key-Ressourcen im Projekt angelegt (`hcloud ssh-key create`, gleiches Anlegen-falls-fehlend-Muster wie die Firewall), damit `--ssh-key` sie bei `server create` referenzieren kann — Hetzners Cloud-Init injiziert sie automatisch in `root`s `authorized_keys`, der Server ist direkt nach Erstellung per Admin-Key erreichbar, kein Umgang mit einem API-Root-Passwort nötig.
*   **Keine Festplattenverschlüsselung (Art. 32) — bewusst:** Deckt Hetzners AV-Vertrag bereits ab (Anlage 2 § 4 „Datenträgerkontrolle": Löschung/Zerstörung von Datenträgern nach Auftragsende, jährlich auditiert). Eigene Verschlüsselung wäre zudem strukturell schwach — Hetzner Cloud ist virtualisiert, ein Boot-Keyfile läge auf demselben Datenträger wie die Daten selbst. Zusätzliche Komplexität für ein vertraglich abgedecktes Risiko widerspricht `rules.md` Abschnitt 1. Die Cyber-Versicherung hat das am 03.09.2026 schriftlich bestätigt: „Eine Verschlüsselung der Festplatten wird von unseren Bedingungen nicht gefordert, wir empfehlen diese jedoch dringend zum Schutz vor physischem Diebstahl." Die Empfehlung zielt auf genau das Risiko, das hier bei Hetzner liegt und vom AV-Vertrag getragen wird — sie ändert den Verzicht deshalb nicht, sondern begründet ihn schärfer. Beide Admins tragen ihn mit. Unberührt davon bleibt die Backup-Verschlüsselung per `age` (`backup.md`): die folgt aus `rules.md` Abschnitt 2 (alles, was Schülerdaten führt und den Host verlässt), nicht aus einer Versicherungsauflage.
*   Firewall-Portliste kommt aus einer gemeinsamen `ports.yml` in `wb-vps/infra/`, die auch das UFW-Skript der Härtung unten liest — eine Änderung an einer Stelle wirkt auf beide Firewall-Ebenen.
*   **Kein Terraform/OpenTofu (bewusst):** würde die hand-geschriebenen Existenzprüfungen (die `ensure_*`-Funktionen samt Python-Helfern, ~190 Zeilen) durch ~70 Zeilen HCL ersetzen — das State-File wiegt schwerer. Das Skript konvergiert ohne Vorwissen: gegen ein leeres Projekt, einen bestehenden Server und einen in der Console veränderten gleichermaßen. Ein IaC-State kann das nicht — ohne ihn scheitert das Anlegen an vorhandenen Ressourcen (Import pro Ressource nötig), mit veraltetem State will das Tool zerstören und neu anlegen. Er müsste also als zweiter Kanal neben dem Passwortmanager zwischen den Admins verteilt werden oder in einem Remote-Backend liegen (neuer Dienst, neues Credential, AVV-Prüfung) — beides schwächt die Neuaufsetzbarkeit aus `rules.md` Abschnitt 6. Dazu deckt IaC nur diese Phase ab; die Host-Konfiguration darunter und in `container.md` bleibt ohnehin selbst-idempotent. **Neu zu bewerten**, sobald `infra/` über Server + Firewall + SSH-Keys hinauswächst (DNS-Records, Volumes, Load-Balancer, zweite Umgebung): dann skaliert Prüf-vor-Aktion schlechter als HCL und `plan` als Diff vor der Änderung wird den State-Aufwand wert.
*   **Keine `hetzner.hcloud`-Collection (bewusst):** Ansible würde Server, Firewall und SSH-Keys genauso zustandslos konvergieren wie die `ensure_*`-Funktionen — Module fragen die API ab, ein State-File gibt es bei Ansible nicht; der Terraform-Grund darüber trägt hier also nicht. Sie würde dieselben ~190 Zeilen samt Python-Helfern und deren Tests durch rund ein Dutzend deklarative Tasks ersetzen. Preis: eine Collection — und damit genau die Eigenschaft, an der `rules.md` Abschnitt 4 die billige Ablösbarkeit von Ansible festmacht (reines `ansible.builtin`, Wegfall kostet nur Übersetzung); dazu ein zweiter Installationsweg auf jeder Admin-Maschine, `ansible-galaxy` neben dem Distributionspaket, das `wb-vps/setup/preflight.sh` prüft. **Neu zu bewerten an derselben Schwelle wie Terraform:** sobald `infra/` über Server + Firewall + SSH-Keys hinauswächst.
*   Jeder Admin nutzt seinen eigenen Hetzner-API-Token statt eines geteilten.
*   Output: Server-IP (bei Hetzner Cloud sofort und dauerhaft bei Server-Erstellung vergeben, ändert sich nicht bei Reboot).

## Härtung des laufenden Hosts

Ansible-Rolle (`rules.md` Abschnitt 1), läuft über normales SSH gegen den laufenden Host — immer als `root`, da der `deploy`-User kein Root ist und ohnehin erst durch diese Phase angelegt wird. Keine Inventory-Datei: die IP aus Phase 1 wird als Ein-Host-Inventar übergeben (`-i "<ip>,"`), damit die Server-Adresse nur an einer Stelle steht. Konstanten liegen in `ansible/group_vars/all.yml`, die Port- und Admin-Listen bleiben in `infra/ports.yml` bzw. `setup/admins.yml` — dieselben Dateien, die auch Phase 1 liest.

*   **Key-Pflege:** Host-`authorized_keys` idempotent pflegen (Quelle: `wb-vps/setup/admins.yml`; Admin hinzufügen/entfernen, ein Key pro Admin, kein geteilter Key/Keyset — analog zum Hetzner-API-Token, jeder Admin nutzt seinen eigenen statt eines geteilten). Läuft als eigener Schritt in derselben Rolle — Neuanlage eines Servers bekommt die Keys bereits über Cloud-Init in Phase 1, dieses Skript pflegt sie danach auf einem bereits laufenden Host nach.
*   **Kein separates Linux-Useraccount pro Admin (bewusst):** alle Admin-Keys landen in `root`s `authorized_keys` — ein geteilter Root-Account mit individueller Zurechenbarkeit über den Key, statt separater Accounts + `sudo`. Root-Login per SSH bleibt aktiv, nicht deaktiviert — es ist der einzige Zugriffsweg für Admins. Separate Accounts wären eine zusätzliche technische Maßnahme gegen die eigene Root-Ebene und bringen laut Vertrauensgrenze (`rules.md` Abschnitt 2) keinen echten Zugewinn: wer `sudo` hat, ist ohnehin root.
*   **Passphrase-Pflicht für Admin-Keys** (dokumentierte Vorgabe in `wb-vps/setup/admins.yml`, nicht technisch erzwingbar — SSH überträgt den Private Key nie an den Server, eine fehlende Passphrase ist serverseitig nicht erkennbar): schützt gegen einen isoliert geleakten Key (falsch abgelegtes Backup, versehentlicher Commit, Kopie auf falscher Maschine) — nicht gegen volle Kompromittierung der Admin-Maschine selbst, dagegen hilft keine Passphrase.
*   **SSH-Härtung:** `PasswordAuthentication no`, dazu `PermitRootLogin prohibit-password`. Letzteres ist nicht redundant: Hetzners Image liefert `PermitRootLogin yes` in der Hauptkonfiguration, womit der Passwort-Login für Root allein daran hinge, dass `PasswordAuthentication` aus bleibt — zwei Einstellungen für eine Tatsache. Beides steht in einem Drop-in `00-wb-vps.conf`, dessen Namenspräfix entscheidend ist: sshd nimmt den **ersten** gesehenen Wert, und cloud-init legt ein `50-cloud-init.conf` mit `PasswordAuthentication yes` daneben. Port bleibt Standard 22 statt verlagert — bei Key-only-Auth gibt es kein Passwort zu erraten, ein verlagerter Port reduziert also nur Scan-Rauschen im Log statt echten Schutz zu bieten, und kollidiert zudem mit dem Rescue-System (immer Port 22).
*   **Firewall (UFW):** zweite, unabhängige Firewall-Ebene neben der Hetzner Cloud Firewall oben — Rückfallnetz bei deren Ausfall/Fehlkonfiguration. Rootful Podman umgeht sie nicht: gemessen landen dessen nftables-Regeln in einer eigenen Tabelle, deren `accept` UFWs Ketten nicht abkürzt. Veröffentlichte Container-Ports passieren allerdings **nie die INPUT-Kette** — sie werden in PREROUTING per DNAT umgeschrieben und danach geforwardet. Jeder Eintrag aus `ports.yml` bekommt deshalb zusätzlich zum `ufw allow` ein `ufw route allow`, und `DEFAULT_FORWARD_POLICY` steht ausdrücklich auf `DROP`; daran hängt die Zusage dieser Ebene. Zwei weitere Regeln (Container-Egress, Container-DNS) und der Nachweis stehen in `container.md`. Liest dieselbe `ports.yml` wie das hcloud-Skript, Cloud Firewall bleibt Quelle der Wahrheit. UFW filtert IPv4 und IPv6 (Debian-Default `IPV6=yes` in `/etc/default/ufw`), passend zur Dual-Stack-Freigabe der Cloud Firewall. Der SSH-Port bekommt `ufw limit` statt `ufw allow` (UFWs `hashlimit`-basiertes Rate-Limiting, Default 6 Verbindungen/30s pro IP) — die einzige der beiden Ebenen, die Rate-Limiting technisch tatsächlich liefert. Task-Reihenfolge dabei verbindlich: erst `ufw limit` für den SSH-Port, danach erst `ufw default deny incoming` + `ufw enable`, sonst sperrt sich die laufende SSH-Session selbst aus.
*   **UFW-Änderungserkennung liest Programmtext (akzeptiertes Risiko):** `ufw allow`/`limit` melden „Skipping adding existing rule", und daran hängt das `changed`-Ergebnis der sechs UFW-Tasks — der letzte handgeschriebene Zustandscheck der Rolle, also die eine Stelle, an der Ansible nicht liefert, wofür es nach `rules.md` Abschnitt 1 gewählt wurde. Die deklarative Alternative `community.general.ufw` ist eine Collection und kostet dasselbe wie die hcloud-Collection oben. Der Fehlerfall ist stumm, aber harmlos: ändert UFW seine Meldung, meldet jeder Lauf `changed`, ohne dass sich am Host etwas ändert — die Regeln selbst bleiben idempotent, nur die Zusage „ein konvergierter Lauf meldet `changed=0`" fällt aus. **Neu zu bewerten**, wenn sie real bricht.
*   **Kein fail2ban auf Host-Ebene** (bewusste Vereinfachung, `rules.md` Abschnitt 1): Key-only-Auth lässt kein Passwort zum Erraten, und `ufw limit` (oben) rate-limitet SSH-Verbindungen bereits — gegen einen echten sshd-Exploit hülfe fail2ban ohnehin nicht, da es erst nach wiederholten Versuchen bannt. Kommt erst mit der App-Stack-Architektur, dann als Jail gegen die Access-Logs des Reverse-Proxys, der ein konkretes Ziel hat.
*   **Verschlüsseltes Swap:** Swapfile mit zufälligem, bei jedem Boot neu generiertem Schlüssel (`/etc/crypttab`, `cipher=aes-xts-plain64`, `/dev/urandom` als Schlüsselquelle) — kein persistenter Schlüssel, kein Break-Glass/Header-Backup nötig, verhindert Klartext-DB-Daten/JWT-Claims im Swap. Schlägt das Setup fehl, läuft der Host den betroffenen Boot ohne Swap statt mit Klartext-Swap. Der Boot-Vorgang selbst braucht dafür kein Netzwerk mehr — kein eigener Pre-Boot-Netzwerkdienst, keine zugehörige Angriffsfläche. **Zwingend dazu die Pakete `systemd-cryptsetup` und `cryptsetup`:** ohne es verarbeitet beim Boot niemand die `/etc/crypttab` — Debian maskiert sein eigenes `cryptdisks.service`, und der Generator, der an dessen Stelle tritt, liegt in diesem separaten Paket. Der Ausfall ist stumm und tritt erst beim Neustart auf: systemd wartet 90 Sekunden auf ein `/dev/mapper/cryptswap`, das nie erscheint, `swap.target` scheitert, der Host läuft ohne Swap weiter. Da er wöchentlich rebootet, wäre das der Normalzustand gewesen. Live gegen `db-prod-fsn-01` gefunden und behoben, Bootzeit danach 17 s.
*   **unattended-upgrades:** Konfiguration inkl. `Remove-Unused-Kernel-Packages` explizit aktiv, automatischer Reboot in einem festen wöchentlichen Wartungsfenster (Samstag, 03:00 Uhr — `Unattended-Upgrade::Automatic-Reboot` bleibt aus, ein eigener systemd-Timer `wb-vps-reboot-if-required.timer` rebootet stattdessen nur bei Bedarf zur festen Kalenderzeit `wb_maintenance_window_calendar`, Konstante in `wb-vps/ansible/group_vars/all.yml` — `Automatic-Reboot-Time` selbst kennt nur eine Uhrzeit, keinen Wochentag; `rules.md` Abschnitt 2 — der anschließende Boot braucht keine menschliche Aktion mehr). Origin-Pattern-Liste bleibt bei den Debian-Standard-Origins: die Container-Runtime (`container.md`) kommt aus Debian main und wird davon bereits abgedeckt, ein Eintrag für ein Fremd-Repo ist nicht nötig. Die Muster referenzieren `${distro_codename}` statt eines festen Codenamens und folgen damit einem Distributions-Upgrade selbst — nach dem Wechsel auf Debian 13 live gegen `db-prod-fsn-01` bestätigt (`unattended-upgrade --dry-run` löst auf `trixie` auf).
*   **Persistentes journald:** `Storage=persistent` explizit gesetzt (`/etc/systemd/journald.conf.d/`), statt sich auf Debians Default `auto` und den zufälligen Umstand zu verlassen, dass Hetzners Image `/var/log/journal` schon vorab anlegt — sonst würden Host-Logs beim wöchentlichen Reboot oben unbemerkt verloren gehen, inklusive der für die 72h-Meldefrist (Art. 33, `container.md`) relevanten Audit-Spur.
*   **Kernel-Hardening (Sysctl):** `kernel.kptr_restrict=1` (Kernel-Pointer in `/proc/kallsyms` etc. für unprivilegierte Prozesse verborgen, schließt einen KASLR-Bypass-Weg für einen lokalen Kernel-Exploit) und `kernel.yama.ptrace_scope=1` (Ptrace nur zwischen Eltern-/Kind-Prozessen) — beides Debian-Default `0`, beides ohne Funktionsverlust auf diesem Host. `ptrace_scope` schützt hier Prozesse desselben Nutzers voreinander, was mit `--userns=auto` je Container ohnehin nur noch eingeschränkt greift — es bleibt trotzdem kostenlos richtig.
*   **Monitoring-Heartbeat:** Host-Cronjob/systemd-Timer, alle 15 Minuten: pingt bei Root-Volume-Disk-Space unter 85% den healthchecks.io-Check (Ping-URL als Secret analog zu den übrigen Phase-2-Secrets behandelt); derselbe Lauf lässt den Check zusätzlich fehlschlagen, wenn `/var/run/reboot-required` seit mehr als 7 Tagen existiert oder der letzte `apt-daily-upgrade.service`-Lauf fehlgeschlagen ist (`systemctl is-failed`) — kein zweiter Check nötig, ein stillschweigend fehlgeschlagener Patch-Lauf zählt sonst als nicht vorhanden. healthchecks.io ist der Dead-Man's-Switch: bei Überschreiten der Schwelle oder ausbleibendem Heartbeat schlägt es per E-Mail Alarm — an ein Sammelpostfach, in dem beide Admins und die Geschäftsführung sitzen, nie an eine personenbezogene Adresse. Läuft unabhängig von der Container-Runtime, rein auf Host-Ebene. Anbieter-/AVV-Details: `dsgvo.md`.
*   **`deploy`-User:** legt einen eingeschränkten `deploy`-SSH-User an (kein Root) — die Schnittstelle, über die das Ausrollen andockt (`deploy.md`).
    *   Kein externer CI-Runner (`container.md`) — Build/Deploy laufen direkt auf der VPS. Auslöser: der vorhandene Admin-Key (`admins.yml`-Muster), zusätzlich in `deploy`s `authorized_keys` eingetragen und dort per `command="git-shell ..."` auf Git-Operationen beschränkt — kein separater Key-Typ nötig, da immer ein vertrauter Admin auslöst.
    *   Womit der `deploy`-User Container startet, richtet die Container-Runtime ein (`container.md`): eine einzige per `sudo` erlaubte systemd-Unit, samt Bare-Repo und Hook. Hier wird nur der User selbst angelegt; seine `authorized_keys` schreibt Phase 3, weil erst dort feststeht, was der Schlüssel darf.
*   **Secret-Dateien:** schreibt die `secrets.env` als Ganzes root-only auf den Host (`/etc/wb-vps/secrets.env`, 0600). Die einzelnen Secret-Dateien der App-Stack-Architektur (DB-Rollen-Passwörter — Runtime/Migration/Backup, Entra-ID-Client-Secret) entstehen daraus beim Deploy (`container.md`), mit der Container-UID als Eigentümer statt `deploy` — unter rootful startet Root die Container, `deploy` bekommt die Werte nie zu Gesicht.
    *   **Format:** flache `KEY=Wert`-Zeilen (kein YAML) — per `source` direkt im Bash-Skript lesbar, kein zusätzlicher Parser nötig, und ohne Einrückungsregeln auch für Nicht-IT-Profis fehlerfrei von Hand pflegbar. Die erwarteten Keys stehen als Schema in `wb-vps/setup/secrets.example.env` (nur Keys, keine Werte, in Git) — verhindert, dass die Feldliste nur im Kopf eines Admins existiert.
    *   **Ablage:** Die echte, befüllte `secrets.env` liegt als Datei-Anhang an einem Eintrag in der gemeinsamen KeePass-Datenbank, nie in Git — die Datenbankdatei selbst liegt im bestehenden M365-Tenant der Schule (SharePoint/OneDrive), für alle Admins erreichbar ohne eigenen Sync-Mechanismus. **Voraussetzung:** Der ausführende Admin lädt den Anhang vorher lokal herunter, das Skript liest ihn von dort und schreibt die Werte per SSH auf den Host — die lokale Kopie wird danach gelöscht. Bearbeiten (z. B. bei Rotation): Anhang herunterladen, betroffene `KEY=Wert`-Zeile im Texteditor ändern, aktualisierte Datei wieder als Anhang hochladen.
