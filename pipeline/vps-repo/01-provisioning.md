# Phase 1 — Provisioning

`[AUTOMATISIERT — wb-vps/infra/]`

Idempotentes Skript gegen das offizielle `hcloud`-CLI:

*   Prüft per `hcloud server describe` anhand des festen Servernamens `db-prod-fsn-01` + Hetzner-Label `weltenbaum` (beide als Konstante in `wb-vps/infra/`), ob der Server schon existiert, legt ihn sonst neu an.
*   Die Firewall wird davon unabhängig bei jedem Skriptlauf idempotent auf den Soll-Zustand aus `ports.yml` gebracht (`hcloud firewall`-Regeln per festem Namen anlegen falls fehlend, sonst per `set-rules` synchronisieren) — nicht nur bei Server-Neuanlage, damit spätere `ports.yml`-Änderungen auch gegen einen bereits bestehenden Server automatisiert nachgezogen werden. Jede Freigabe-Regel wird für beide Quell-Familien gesetzt (`0.0.0.0/0` **und** `::/0`) — Hetzner wendet eine Regel nicht automatisch auf beide an, sonst bliebe der IPv6-Pfad (Hetzners natives Dual-Stack-Networking auf dem Standard-Image) ungefiltert.
*   Zero-Trust nach außen: eingehend per Default nur Port 22 (SSH) sowie 80/443 (späterer öffentlicher App-Stack-Dienst) offen, alles andere zu. Datenbank-/Backend-Ports bleiben nach außen komplett geschlossen — welche das konkret sind, entscheidet sich mit der App-Stack-Architektur. **Akzeptiertes Risiko:** kein Egress-Filtering — Schutzziel ist der eingehende Zugriff, nicht Exfiltration nach einem Einbruch.
*   **Kein eigenes DDoS-Mitigation-Tool (bewusst):** andere Bedrohung als der Bruteforce-Schutz aus [Phase 2](02-hardening.md) — DDoS ist Ressourcenerschöpfung durch Volumen (SYN-/Bandbreiten-Flood), kein Credential-Raten, `ufw limit` (SSH-Rate-Limiting) wirkt hier nicht. Hetzner filtert volumetrische Angriffe bereits am Netzwerk-Perimeter, bevor Traffic die VPS erreicht — Hoster-native Lösung statt Eigenbau (`rules.md` Abschnitt 1 Punkt 2, Abschnitt 2 Vertrauensgrenze: Hetzner gilt als vertrauenswürdig).
*   Servertyp `cx33` (4 vCPU shared, 8GB RAM, 80GB NVMe SSD — für den späteren App-Stack einer kleinen Schule ausreichend dimensioniert), Region `fsn1` (Falkenstein, Deutschland — einfachste DSGVO-Begründung ohne Drittland-Transfer), beide als Konstante in `wb-vps/infra/`.
*   `--image debian-13` ist das tatsächlich laufende Image — Hetzners Standard-Cloud-Image, unverändert übernommen, kein eigener Wipe-/Rescue-/Installationsschritt, kein individuelles Partitionslayout. Die Version ist nicht beliebig: Debian 13 (trixie) liefert Podman 5.4, Debian 12 nur 4.3 — die Eigenschaften, auf denen [Phase 3](03-podman-install.md) beruht, hängen daran. Die Admin-Public-Keys aus `wb-vps/setup/admins.yml` (bewusst dieselbe einzige Key-Quelle wie in Phase 2, `rules.md` Abschnitt 3 — liegt in `setup/`, wird aber auch hier vom `infra/`-Skript gelesen) werden vom Skript zuvor idempotent als Hetzner-SSH-Key-Ressourcen im Projekt angelegt (`hcloud ssh-key create`, gleiches Anlegen-falls-fehlend-Muster wie die Firewall), damit `--ssh-key` sie bei `server create` referenzieren kann — Hetzners Cloud-Init injiziert sie automatisch in `root`s `authorized_keys`, der Server ist direkt nach Erstellung per Admin-Key erreichbar, kein Umgang mit einem API-Root-Passwort nötig.
*   **Keine Festplattenverschlüsselung (Art. 32) — bewusst:** Deckt Hetzners AV-Vertrag bereits ab (Anlage 2 § 4 „Datenträgerkontrolle": Löschung/Zerstörung von Datenträgern nach Auftragsende, jährlich auditiert). Eigene Verschlüsselung wäre zudem strukturell schwach — Hetzner Cloud ist virtualisiert, ein Boot-Keyfile läge auf demselben Datenträger wie die Daten selbst. Zusätzliche Komplexität für ein vertraglich abgedecktes Risiko widerspricht `rules.md` Abschnitt 1. Die vorliegenden Bedingungen der Cyber-Versicherung fordern keine Verschlüsselung at rest — weder für den Host noch für Backups; beide Admins tragen den Verzicht mit. Rückbestätigung ist als reine Absicherung in `TODO.md` vermerkt. Unberührt davon bleibt die Backup-Verschlüsselung per `age` (`idea/05-backup-recovery.md`): die folgt aus `rules.md` Abschnitt 2 (alles, was Schülerdaten führt und den Host verlässt), nicht aus einer Versicherungsauflage.
*   Firewall-Portliste kommt aus einer gemeinsamen `ports.yml` in `wb-vps/infra/`, die auch das UFW-Skript aus [Phase 2](02-hardening.md) liest — eine Änderung an einer Stelle wirkt auf beide Firewall-Ebenen.
*   **Kein Terraform/OpenTofu (bewusst):** würde die hand-geschriebenen Existenzprüfungen (die `ensure_*`-Funktionen samt Python-Helfern, ~190 Zeilen) durch ~70 Zeilen HCL ersetzen — das State-File wiegt schwerer. Das Skript konvergiert ohne Vorwissen: gegen ein leeres Projekt, einen bestehenden Server und einen in der Console veränderten gleichermaßen. Ein IaC-State kann das nicht — ohne ihn scheitert das Anlegen an vorhandenen Ressourcen (Import pro Ressource nötig), mit veraltetem State will das Tool zerstören und neu anlegen. Er müsste also als zweiter Kanal neben dem Passwortmanager zwischen den Admins verteilt werden oder in einem Remote-Backend liegen (neuer Dienst, neues Credential, AVV-Prüfung) — beides schwächt die Neuaufsetzbarkeit aus `rules.md` Abschnitt 6. Dazu deckt IaC nur diese Phase ab; die Host-Konfiguration in [Phase 2](02-hardening.md)/[Phase 3](03-podman-install.md) bleibt ohnehin selbst-idempotent. **Neu zu bewerten**, sobald `infra/` über Server + Firewall + SSH-Keys hinauswächst (DNS-Records, Volumes, Load-Balancer, zweite Umgebung): dann skaliert Prüf-vor-Aktion schlechter als HCL und `plan` als Diff vor der Änderung wird den State-Aufwand wert.
*   **Keine `hetzner.hcloud`-Collection (bewusst):** Ansible würde Server, Firewall und SSH-Keys genauso zustandslos konvergieren wie die `ensure_*`-Funktionen — Module fragen die API ab, ein State-File gibt es bei Ansible nicht; der Terraform-Grund darüber trägt hier also nicht. Sie würde dieselben ~190 Zeilen samt Python-Helfern und deren Tests durch rund ein Dutzend deklarative Tasks ersetzen. Preis: eine Collection — und damit genau die Eigenschaft, an der `rules.md` Abschnitt 4 die billige Ablösbarkeit von Ansible festmacht (reines `ansible.builtin`, Wegfall kostet nur Übersetzung); dazu ein zweiter Installationsweg auf jeder Admin-Maschine, `ansible-galaxy` neben dem Distributionspaket, das `wb-vps/setup/preflight.sh` prüft. **Neu zu bewerten an derselben Schwelle wie Terraform:** sobald `infra/` über Server + Firewall + SSH-Keys hinauswächst.
*   Jeder Admin nutzt seinen eigenen Hetzner-API-Token statt eines geteilten.
*   Output: Server-IP (bei Hetzner Cloud sofort und dauerhaft bei Server-Erstellung vergeben, ändert sich nicht bei Reboot).
