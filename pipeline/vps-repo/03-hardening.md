# Phase 3 — Key-Pflege + Host-Hardening

`[AUTOMATISIERT — Shell-Skript, vps/setup/]`

Idempotentes Bash-Skript im Stil von Phase 1/2 (kein Ansible — bei genau einer VPS mit statischer IP derselbe „Overkill"-Grund wie der Terraform-Verzicht in [Phase 1](01-provisioning.md), IP wird als Skriptparameter/Konstante übergeben, keine Inventory-Datei nötig), läuft über normales SSH gegen den automatisch entschlüsselten, laufenden Host — immer als `root`, da der `deploy`-User laut `project-parts.md` kein Root ist und ohnehin erst durch diese Phase angelegt wird.

## Aufgaben

*   **Key-Pflege:** Host-`authorized_keys` idempotent pflegen (Quelle: `vps/setup/admins.yml`; Admin hinzufügen/entfernen, ein Key pro Admin, kein geteilter Key/Keyset).
*   **SSH-Härtung:** `PasswordAuthentication no`.
*   **Firewall (UFW):** zweite Firewall-Ebene neben der Hetzner Cloud Firewall aus [Phase 1](01-provisioning.md) — liest dieselbe `ports.yml` wie das hcloud-Skript, Cloud Firewall bleibt Quelle der Wahrheit. Der SSH-Port bekommt `ufw limit` statt `ufw allow` (UFWs `hashlimit`-basiertes Rate-Limiting, Default 6 Verbindungen/30s pro IP) — das ist die einzige der beiden in `idea/02-netzwerk-firewall.md` genannten Ebenen, die Rate-Limiting technisch tatsächlich liefert. Skript-Reihenfolge dabei verbindlich: erst `ufw limit` für den SSH-Port, danach erst `ufw default deny incoming` + `ufw enable`, sonst sperrt sich die laufende SSH-Session selbst aus.
*   **fail2ban:** schützt Host-SSH gegen Verbindungsflut/Exploit-Versuche gegen sshd, nicht gegen Bruteforce — Key-only-Auth lässt kein Passwort zum Erraten. Ein zweiter Jail für App-Stack-Rate-Limiting kommt hinzu, sobald Reverse-Proxy/Log-Format der App-Stack-Architektur feststehen (`idea/02-netzwerk-firewall.md`).
*   **unattended-upgrades:** Konfiguration inkl. APT-Hook für automatisches `update-initramfs`/`update-grub` nach Kernel-Updates, `Remove-Unused-Kernel-Packages` explizit aktiv (verhindert, dass alte Kernel-/Initramfs-Images die feste 512MB-`/boot`-Partition aus [Phase 2](02-rescue-install.md) volllaufen lassen), automatischer Reboot in einem festen wöchentlichen Wartungsfenster (`rules.md` Abschnitt 2 — der anschließende Boot braucht dank automatischem Keyfile-Unlock keine menschliche Aktion mehr). Origin-Pattern-Liste enthält zusätzlich zu den Debian-Standard-Origins die Docker-APT-Repo-Origin (`download.docker.com`) — sonst patcht `unattended-upgrades` per Default nur Debian-eigene Origins, der in [Phase 4a](04a-docker-install.md) installierte Docker-Daemon liefe trotz monatlicher Patch-Kadenz sonst dauerhaft ungepatcht, ohne dass das als Fehlschlag auffällt (Update wird nie versucht statt zu scheitern). Eintrag wirkt unabhängig davon, ob das Docker-Repo zum Zeitpunkt dieses Skriptlaufs schon existiert.
*   **Monitoring-Heartbeat:** Host-Cronjob/systemd-Timer für den healthchecks.io-Heartbeat (Disk-Space-Check + `reboot-required`-Check + `unattended-upgrades`-Fehlschlag-Check alle 15 Minuten, Ping-URL als Secret analog zu den übrigen Phase-3-Secrets behandelt) — Dead-Man's-Switch über healthchecks.io (kostenloser Hobbyist-Plan, Hetzner Deutschland), siehe `idea/01-boot-verschluesselung.md`.
*   **`deploy`-User:** legt einen eingeschränkten `deploy`-SSH-User an (kein Root) — die Schnittstelle, über die [Phase 4b](../app-stack-repo/04b-app-stack-deploy.md) später andockt.
    *   Der Public Key für den CI-Deploy-Zugriff (Bootstrap siehe [Runbook, Schritt 6](../runbook.md), sobald die CI/CD-Plattform des App-Stack-Repos feststeht) wird dabei idempotent wie die übrigen Admin-Keys in die `authorized_keys` des `deploy`-Users provisioniert.
    *   Für den in [Phase 4a](04a-docker-install.md) installierten Rootless-Docker-Daemon zusätzlich einmalig (als Root, danach nie wieder nötig): `setcap cap_net_bind_service=ep` auf das `rootlesskit`-Binary sowie `loginctl enable-linger deploy`, damit Port 80/443 gebunden werden kann und der Daemon auch ohne aktive SSH-Session weiterläuft.
*   **Secret-Dateien:** schreibt die Secret-Dateien der App-Stack-Architektur (z. B. DB-Zugangsdaten, Identitätsanbieter-Secret, Backup-Repo-Passwort — konkrete Liste folgt mit der Architektur) aus der age-verschlüsselten Secrets-Datei mit `deploy`-User-Ownership auf den Host (`idea/03-container-anwendung.md`) — [Phase 4b](../app-stack-repo/04b-app-stack-deploy.md) mountet sie nur noch, die CI/CD-Pipeline bekommt die Werte nie zu Gesicht.
