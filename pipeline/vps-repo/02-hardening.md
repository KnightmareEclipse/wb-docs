# Phase 2 — Key-Pflege + Host-Hardening

`[AUTOMATISIERT — Shell-Skript, vps/setup/]`

Idempotentes Bash-Skript im Stil von Phase 1 (kein Ansible, `rules.md` Abschnitt 1 — IP wird als Skriptparameter/Konstante übergeben, keine Inventory-Datei nötig), läuft über normales SSH gegen den laufenden Host — immer als `root`, da der `deploy`-User laut `project-parts.md` kein Root ist und ohnehin erst durch diese Phase angelegt wird.

## Aufgaben

*   **Key-Pflege:** Host-`authorized_keys` idempotent pflegen (Quelle: `vps/setup/admins.yml`; Admin hinzufügen/entfernen, ein Key pro Admin, kein geteilter Key/Keyset).
*   **SSH-Härtung:** `PasswordAuthentication no`.
*   **Firewall (UFW):** zweite Firewall-Ebene neben der Hetzner Cloud Firewall aus [Phase 1](01-provisioning.md) — liest dieselbe `ports.yml` wie das hcloud-Skript, Cloud Firewall bleibt Quelle der Wahrheit. UFW filtert IPv4 und IPv6 (Debian-Default `IPV6=yes` in `/etc/default/ufw`), passend zur Dual-Stack-Freigabe der Cloud Firewall. Der SSH-Port bekommt `ufw limit` statt `ufw allow` (UFWs `hashlimit`-basiertes Rate-Limiting, Default 6 Verbindungen/30s pro IP) — das ist die einzige der beiden in `idea/02-netzwerk-firewall.md` genannten Ebenen, die Rate-Limiting technisch tatsächlich liefert. Skript-Reihenfolge dabei verbindlich: erst `ufw limit` für den SSH-Port, danach erst `ufw default deny incoming` + `ufw enable`, sonst sperrt sich die laufende SSH-Session selbst aus.
*   **Kein fail2ban auf Host-Ebene** (bewusste Vereinfachung, `rules.md` Abschnitt 1): Key-only-Auth lässt kein Passwort zum Erraten, und `ufw limit` (oben) rate-limitet SSH-Verbindungen bereits — gegen einen echten sshd-Exploit hülfe fail2ban ohnehin nicht, da es erst nach wiederholten Versuchen bannt. fail2ban kommt erst mit der App-Stack-Architektur und dann mit einem Jail gegen die Access-Logs des Reverse-Proxys, der ein konkretes Ziel hat (`idea/02-netzwerk-firewall.md`).
*   **Verschlüsseltes Swap:** Swapfile mit zufälligem, bei jedem Boot neu generiertem Schlüssel (`/etc/crypttab`, `/dev/urandom` als Schlüsselquelle) — kein persistenter Schlüssel, kein Break-Glass/Header-Backup nötig (`idea/01-boot-verschluesselung.md`).
*   **unattended-upgrades:** Konfiguration inkl. `Remove-Unused-Kernel-Packages` explizit aktiv, automatischer Reboot in einem festen wöchentlichen Wartungsfenster (`rules.md` Abschnitt 2 — der anschließende Boot braucht keine menschliche Aktion mehr). Origin-Pattern-Liste enthält zusätzlich zu den Debian-Standard-Origins die Docker-APT-Repo-Origin (`download.docker.com`) — sonst patcht `unattended-upgrades` per Default nur Debian-eigene Origins, der in [Phase 3](03-docker-install.md) installierte Docker-Daemon liefe trotz monatlicher Patch-Kadenz sonst dauerhaft ungepatcht, ohne dass das als Fehlschlag auffällt (Update wird nie versucht statt zu scheitern). Eintrag wirkt unabhängig davon, ob das Docker-Repo zum Zeitpunkt dieses Skriptlaufs schon existiert.
*   **Monitoring-Heartbeat:** Host-Cronjob/systemd-Timer für den healthchecks.io-Heartbeat (Disk-Space-Check + `reboot-required`-Check + `unattended-upgrades`-Fehlschlag-Check alle 15 Minuten, Ping-URL als Secret analog zu den übrigen Phase-2-Secrets behandelt) — Dead-Man's-Switch über healthchecks.io (kostenloser Hobbyist-Plan, Hetzner Deutschland), siehe `idea/01-boot-verschluesselung.md`.
*   **`deploy`-User:** legt einen eingeschränkten `deploy`-SSH-User an (kein Root) — die Schnittstelle, über die [Phase 4](../app-stack-repo/04-app-stack-deploy.md) später andockt.
    *   Der Public Key für den CI-Deploy-Zugriff (Bootstrap siehe [Runbook, Schritt 5](../runbook.md), sobald die CI/CD-Plattform des App-Stack-Repos feststeht) wird dabei idempotent wie die übrigen Admin-Keys in die `authorized_keys` des `deploy`-Users provisioniert.
    *   Die Root-Einmalschritte, die den Rootless-Docker-Daemon des `deploy`-Users betreffen (`setcap` auf das `rootlesskit`-Binary, `enable-linger`), laufen erst in [Phase 3](03-docker-install.md) — dort existiert das Binary, hier wird nur der User selbst angelegt.
*   **Secret-Dateien:** schreibt die Secret-Dateien der App-Stack-Architektur (z. B. DB-Zugangsdaten, Identitätsanbieter-Secret, Backup-Repo-Passwort — konkrete Liste folgt mit der Architektur) aus `secrets.env` mit `deploy`-User-Ownership auf den Host (`idea/03-container-anwendung.md`) — [Phase 4](../app-stack-repo/04-app-stack-deploy.md) mountet sie nur noch, die CI/CD-Pipeline bekommt die Werte nie zu Gesicht.
    *   **Format:** flache `KEY=Wert`-Zeilen (kein YAML) — per `source` direkt im Bash-Skript lesbar, kein zusätzlicher Parser nötig, und ohne Einrückungsregeln auch für Nicht-IT-Profis fehlerfrei von Hand pflegbar. Die erwarteten Keys stehen als Schema in `vps/setup/secrets.example.env` (nur Keys, keine Werte, in Git) — verhindert, dass die Feldliste nur im Kopf eines Admins existiert.
    *   **Ablage:** Die echte, befüllte `secrets.env` liegt als Datei-Anhang an einem Eintrag in der gemeinsamen KeePass-Datenbank (`idea/01-boot-verschluesselung.md`), nie in Git. **Voraussetzung:** Der ausführende Admin lädt den Anhang vorher lokal herunter, das Skript liest ihn von dort und schreibt die Werte per SSH auf den Host — die lokale Kopie wird danach gelöscht. Bearbeiten (z. B. bei Rotation): Anhang herunterladen, betroffene `KEY=Wert`-Zeile im Texteditor ändern, aktualisierte Datei wieder als Anhang hochladen.
