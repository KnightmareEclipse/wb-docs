# Phase 2 — Key-Pflege + Host-Hardening

`[AUTOMATISIERT — Shell-Skript, wb-vps/setup/]`

Idempotentes Bash-Skript im Stil von Phase 1 (kein Ansible, `rules.md` Abschnitt 1 — IP wird als Skriptparameter/Konstante übergeben, keine Inventory-Datei nötig), läuft über normales SSH gegen den laufenden Host — immer als `root`, da der `deploy`-User laut `project-parts.md` kein Root ist und ohnehin erst durch diese Phase angelegt wird.

## Aufgaben

*   **Key-Pflege:** Host-`authorized_keys` idempotent pflegen (Quelle: `wb-vps/setup/admins.yml`; Admin hinzufügen/entfernen, ein Key pro Admin, kein geteilter Key/Keyset — analog zum Hetzner-API-Token, jeder Admin nutzt seinen eigenen statt eines geteilten). Eigenes Skript `setup/sync-admin-keys.sh`, unabhängig von den übrigen Schritten unten (die in `harden.sh` laufen) — Neuanlage eines Servers bekommt die Keys bereits über Cloud-Init in Phase 1, dieses Skript pflegt sie danach auf einem bereits laufenden Host nach.
*   **Kein separates Linux-Useraccount pro Admin (bewusst):** alle Admin-Keys landen in `root`s `authorized_keys` — ein geteilter Root-Account mit individueller Zurechenbarkeit über den Key, statt separater Accounts + `sudo`. Root-Login per SSH bleibt aktiv, nicht deaktiviert — es ist der einzige Zugriffsweg für Admins. Separate Accounts wären eine zusätzliche technische Maßnahme gegen die eigene Root-Ebene und bringen laut Vertrauensgrenze (`rules.md` Abschnitt 2) keinen echten Zugewinn: wer `sudo` hat, ist ohnehin root.
*   **Passphrase-Pflicht für Admin-Keys** (dokumentierte Vorgabe in `wb-vps/setup/admins.yml`, nicht technisch erzwingbar — SSH überträgt den Private Key nie an den Server, eine fehlende Passphrase ist serverseitig nicht erkennbar): schützt gegen einen isoliert geleakten Key (falsch abgelegtes Backup, versehentlicher Commit, Kopie auf falscher Maschine) — nicht gegen volle Kompromittierung der Admin-Maschine selbst, dagegen hilft keine Passphrase.
*   **SSH-Härtung:** `PasswordAuthentication no`. Port bleibt Standard 22 statt verlagert — bei Key-only-Auth gibt es kein Passwort zu erraten, ein verlagerter Port reduziert also nur Scan-Rauschen im Log statt echten Schutz zu bieten, und kollidiert zudem mit dem Rescue-System (immer Port 22).
*   **Firewall (UFW):** zweite, unabhängige Firewall-Ebene neben der Hetzner Cloud Firewall aus [Phase 1](01-provisioning.md) — Rückfallnetz bei deren Ausfall/Fehlkonfiguration, nicht wegen Docker-eigener iptables-Regeln (Rootless Docker läuft im User-Namespace des `deploy`-Users und fasst die Host-iptables gar nicht an). Liest dieselbe `ports.yml` wie das hcloud-Skript, Cloud Firewall bleibt Quelle der Wahrheit. UFW filtert IPv4 und IPv6 (Debian-Default `IPV6=yes` in `/etc/default/ufw`), passend zur Dual-Stack-Freigabe der Cloud Firewall. Der SSH-Port bekommt `ufw limit` statt `ufw allow` (UFWs `hashlimit`-basiertes Rate-Limiting, Default 6 Verbindungen/30s pro IP) — die einzige der beiden Ebenen, die Rate-Limiting technisch tatsächlich liefert. Skript-Reihenfolge dabei verbindlich: erst `ufw limit` für den SSH-Port, danach erst `ufw default deny incoming` + `ufw enable`, sonst sperrt sich die laufende SSH-Session selbst aus.
*   **Kein fail2ban auf Host-Ebene** (bewusste Vereinfachung, `rules.md` Abschnitt 1): Key-only-Auth lässt kein Passwort zum Erraten, und `ufw limit` (oben) rate-limitet SSH-Verbindungen bereits — gegen einen echten sshd-Exploit hülfe fail2ban ohnehin nicht, da es erst nach wiederholten Versuchen bannt. Kommt erst mit der App-Stack-Architektur, dann als Jail gegen die Access-Logs des Reverse-Proxys, der ein konkretes Ziel hat.
*   **Verschlüsseltes Swap:** Swapfile mit zufälligem, bei jedem Boot neu generiertem Schlüssel (`/etc/crypttab`, `cipher=aes-xts-plain64`, `/dev/urandom` als Schlüsselquelle) — kein persistenter Schlüssel, kein Break-Glass/Header-Backup nötig, verhindert Klartext-DB-Daten/JWT-Claims im Swap. Schlägt das Setup fehl, läuft der Host den betroffenen Boot ohne Swap statt mit Klartext-Swap. Der Boot-Vorgang selbst braucht dafür kein Netzwerk mehr — kein eigener Pre-Boot-Netzwerkdienst, keine zugehörige Angriffsfläche.
*   **unattended-upgrades:** Konfiguration inkl. `Remove-Unused-Kernel-Packages` explizit aktiv, automatischer Reboot in einem festen wöchentlichen Wartungsfenster (Samstag, 03:00 Uhr — `Unattended-Upgrade::Automatic-Reboot` bleibt aus, ein eigener systemd-Timer `wb-vps-reboot-if-required.timer` rebootet stattdessen nur bei Bedarf zur festen Kalenderzeit `MAINTENANCE_WINDOW_CALENDAR`, Konstante in `wb-vps/setup/` — `Automatic-Reboot-Time` selbst kennt nur eine Uhrzeit, keinen Wochentag; `rules.md` Abschnitt 2 — der anschließende Boot braucht keine menschliche Aktion mehr). Origin-Pattern-Liste enthält zusätzlich zu den Debian-Standard-Origins die Docker-APT-Repo-Origin (`download.docker.com`) — sonst patcht `unattended-upgrades` per Default nur Debian-eigene Origins, der in [Phase 3](03-docker-install.md) installierte Docker-Daemon liefe trotz monatlicher Patch-Kadenz sonst dauerhaft ungepatcht, ohne dass das als Fehlschlag auffällt (Update wird nie versucht statt zu scheitern). Eintrag wirkt unabhängig davon, ob das Docker-Repo zum Zeitpunkt dieses Skriptlaufs schon existiert.
*   **Persistentes journald:** `Storage=persistent` explizit gesetzt (`/etc/systemd/journald.conf.d/`), statt sich auf Debians Default `auto` und den zufälligen Umstand zu verlassen, dass Hetzners Image `/var/log/journal` schon vorab anlegt — sonst würden Host-Logs beim wöchentlichen Reboot oben unbemerkt verloren gehen, inklusive der für die 72h-Meldefrist (Art. 33, `idea/03-container-anwendung.md`) relevanten Audit-Spur.
*   **Kernel-Hardening (Sysctl):** `kernel.kptr_restrict=1` (Kernel-Pointer in `/proc/kallsyms` etc. für unprivilegierte Prozesse verborgen, schließt einen KASLR-Bypass-Weg für einen lokalen Kernel-Exploit) und `kernel.yama.ptrace_scope=1` (Ptrace nur zwischen Eltern-/Kind-Prozessen) — beides Debian-Default `0`, beides ohne Funktionsverlust auf diesem Host. `ptrace_scope` wiegt hier schwerer als sonst üblich: der Rootless-Docker-Daemon läuft mit `dockerd`/`containerd`/Shims komplett unter derselben `deploy`-UID (`idea/03-container-anwendung.md`), `scope=0` ließe jeden Prozess, der als `deploy` läuft, jeden anderen — inklusive des Daemons selbst — per Ptrace inspizieren.
*   **Monitoring-Heartbeat:** Host-Cronjob/systemd-Timer, alle 15 Minuten: pingt bei Root-Volume-Disk-Space unter 85% den healthchecks.io-Check (Ping-URL als Secret analog zu den übrigen Phase-2-Secrets behandelt); derselbe Lauf lässt den Check zusätzlich fehlschlagen, wenn `/var/run/reboot-required` seit mehr als 7 Tagen existiert oder der letzte `apt-daily-upgrade.service`-Lauf fehlgeschlagen ist (`systemctl is-failed`) — kein zweiter Check nötig, ein stillschweigend fehlgeschlagener Patch-Lauf zählt sonst als nicht vorhanden. healthchecks.io ist der Dead-Man's-Switch: bei Überschreiten der Schwelle oder ausbleibendem Heartbeat schlägt es per E-Mail Alarm. Läuft unabhängig von Docker, rein auf Host-Ebene. Anbieter-/AVV-Details: `idea/06-dsgvo-organisatorisch.md`.
*   **`deploy`-User:** legt einen eingeschränkten `deploy`-SSH-User an (kein Root) — die Schnittstelle, über die [Phase 4](../app-stack-repo/04-app-stack-deploy.md) später andockt.
    *   Kein externer CI-Runner (`idea/03-container-anwendung.md`) — Build/Deploy laufen direkt auf der VPS über den `deploy`-User selbst. Auslöser: der vorhandene Admin-Key (`admins.yml`-Muster), zusätzlich in `deploy`s `authorized_keys` eingetragen und dort per `command="git-shell ..."` auf Git-Operationen beschränkt (Bootstrap siehe [Runbook, Schritt 5](../runbook.md)) — kein separater Key-Typ nötig, da immer ein vertrauter Admin auslöst.
    *   Die Root-Einmalschritte, die den Rootless-Docker-Daemon des `deploy`-Users betreffen (privilegierte Portfreigabe per `sysctl`, Cgroup-v2-Delegation, `enable-linger`), laufen zusammen mit der eigentlichen Docker-Installation erst in [Phase 3](03-docker-install.md) — hier wird nur der User selbst angelegt.
*   **Secret-Dateien:** schreibt die Secret-Dateien der App-Stack-Architektur (DB-Rollen-Passwörter Runtime/Migration/Backup, Entra-ID-Client-Secret, `age`-Verschlüsselungs-Passphrase) aus `secrets.env` mit `deploy`-User-Ownership auf den Host (`idea/03-container-anwendung.md`) — [Phase 4](../app-stack-repo/04-app-stack-deploy.md) mountet sie nur noch, der Git-Push-Deploy-Auslöser bekommt die Werte nie zu Gesicht.
    *   **Format:** flache `KEY=Wert`-Zeilen (kein YAML) — per `source` direkt im Bash-Skript lesbar, kein zusätzlicher Parser nötig, und ohne Einrückungsregeln auch für Nicht-IT-Profis fehlerfrei von Hand pflegbar. Die erwarteten Keys stehen als Schema in `wb-vps/setup/secrets.example.env` (nur Keys, keine Werte, in Git) — verhindert, dass die Feldliste nur im Kopf eines Admins existiert.
    *   **Ablage:** Die echte, befüllte `secrets.env` liegt als Datei-Anhang an einem Eintrag in der gemeinsamen KeePass-Datenbank, nie in Git — die Datenbankdatei selbst liegt im bestehenden M365-Tenant der Schule (SharePoint/OneDrive), für alle Admins erreichbar ohne eigenen Sync-Mechanismus. **Voraussetzung:** Der ausführende Admin lädt den Anhang vorher lokal herunter, das Skript liest ihn von dort und schreibt die Werte per SSH auf den Host — die lokale Kopie wird danach gelöscht. Bearbeiten (z. B. bei Rotation): Anhang herunterladen, betroffene `KEY=Wert`-Zeile im Texteditor ändern, aktualisierte Datei wieder als Anhang hochladen.
